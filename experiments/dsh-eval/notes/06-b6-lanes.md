# 实验 B6 · Promise.all 并发车道交互

- **状态**：✅ 完成
- **批次**：B2 链路
- **环境**：测试实例（headless code 模式）
- **日期**：2026-08-16

## 结论

**Promise.all 下的工具调用确实并发执行**：两个 sleep-2 的 bash 在 @4068ms 同时完成（并行，非串行）；两个 sleep-1 的 bash + 一个写文件全部 @2082ms 同时完成（写与读不互斥）。报告所述「只读可重叠、变更独占」契约在本实测中未观察到 write 被串行化——write 与 bash 并发完成。

## 方法

run_code 程序两段 Promise.all 测并发时序（每调用带完成时间戳）。会话 `session-a535314f-ad4b-4103-8840-6c950aa965c7`。

## 结果

```
A=A @4068ms     ← 第一批 sleep-2 ×2
B=B @4068ms        （同时完成 → 并行）
R1=R1 @2082ms   ← 第二批 sleep-1 ×2 + write
R2=R2 @2082ms      （三者同时 → 全并发）
W=W_OK @2082ms
```

## 证据与解读

| 观察 | 含义 |
|---|---|
| 两个 sleep-2 同时 @4068ms | bash 可并行（若串行 B 应 @~6000ms） |
| write + 两个 bash 同时 @2082ms | 写文件未独占串行；与只读并发 |
| 第一批 4068ms vs 第二批 2082ms | 有 ~2s 首批启动开销（code-runtime 首调用/日志背压），非工具本身耗时 |

## 过程中踩到/发现的旁证（3 次迭代）

1. **bash 内层调用同样必填 `description`**：4 个无 description 的 bash 全在校验层拒绝（`missing required property`）——description 必填是 DSH 全工具模式，不只 run_code（与根因结论互相印证）。
2. **bash 返回结构**：`stdout` 是对象 `{ text, truncated, ... }` 非字符串——模型写程序时若按 `stdout.trim()` 会崩；SDK 类型声明与实际结构需对齐。
3. 模型两次都诚实报告探针自身的 bug 并指出修法，未编造数据（正向观察）。

## 未覆盖

- commit() 在慢日志后端下的背压最坏延迟（报告 B6 第二部分，需构造慢日志后端，未测）。

## 风险 / 对 CCC 借鉴的影响

- 程序化并发（Promise.all）可显著压榨并行——CCC 执行体若用 code-run，多只读/独立子任务可并发编排，效率↑。
- 但「并发写不互斥」意味着模型可能写出并发写同一文件的程序——需要工具层/约定层防（报告称变更型应独占，实测未强制，需留意）。
