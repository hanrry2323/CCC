## 0. 顶层判断

**这不是"将来风险"，是已经在生产中爆发的工程债务。**

5 份独立审查在 5 个子系统都发现了**结构性同型缺陷**——同一类问题在不同模块重复出现，说明根因不在某个脚本，而是架构层面的统一假设错误：

| 误以为 | 实际 |
|---|---|
| "我们用了 `os.replace()` 就是原子写" | 缺 fsync、缺目录 fsync、缺 journal、缺事务 |
| "我们写了 events.jsonl 就有可观测性" | 异常被吞、缺关键事件、append 无 fsync |
| "我们把 Popen 包了 try/finally 就安全" | finally 只清 pid_file，子进程树不递归 |
| "watchdog 在 = 不会卡死" | watchdog 自己会因 wall-clock 误杀，触发无限重启循环 |
| "Basic Auth + 默认口令就是安全" | 0.0.0.0 + ccc:ccc + LAN 默认放行 = 任何同网段脚本能动控制面 |
| "reviewer 写了 verdict 就完成门禁" | reviewer 可绕过、verdict 空文件兼容、tester 结果不查 |

## 1. 五大根因类别

### 类别 ①：写入非原子 + 状态不一致（**最严重**）

**子证据**（不是孤立 bug，是统一假设错误）：

- 调度核心 #5 — `scripts/engine/active_tasks.py:78-104` 直接 `write_text`，崩溃即截断
- 看板存储 — `scripts/_board_store.py:872-976` `move_task` 先原子生成目标、再 `unlink` 源，进程中断 = 双副本
- 看板存储 — `scripts/_board_store.py:1013-1032` `update_index()` 需调用方手动调；`move_task` 与 index 不同事务，**index 可永久陈旧**
- 看板存储 — `scripts/_board_store.py:1211-1262` `state.md` 在 board lock 释放后单独写，无独立锁；多 slot 可同时 RMW `state.md` 后写覆盖先写
- 执行器 H3 — `scripts/opencode-exec.py:211-215` pid_file 写入窗口期竞态（**Lesson 44 已实锤**）
- 控制面 H1 — `scripts/_ccc_control.py:60-66` `_write_raw` 缺 fsync；**固定 `.tmp` 名 → 并发写覆盖**；对照 `set_mode` 在 disabled 分支（`:191-199`）就 `os.fsync(...)`
- 控制面 M6 — `scripts/chat_server/services/flow_events.py:541` `path.write_text()` truncate-write 无 fsync

**根因**：整个系统把 `fsync / atomic_write / journal` 视为"优化"而非"正确性前提"。每一次"以为原子"都是概率性正确——断电、磁盘满、进程被 SIGKILL 任意一种即打破。

**业务后果**：用户视角的"任务消失"、"卡死"、"重复 launch"几乎都来自这一类。

---

### 类别 ②：可观测性在骗你（**第二严重，因为它掩盖类别 ①**）

**子证据**：

- 控制面+可观测性 #1 — `scripts/ccc-engine.py:317-322` `upstream-probe` 把任意 2xx/4xx 当 healthy；异常写入静默吞；只在状态变化采样，**连续失败/恢复期间无每次探测审计**
- 控制面+可观测性 #2 — `scripts/ccc-engine.py:550-570` `_log_stats` events append 出错也静默
- 控制面+可观测性 #5 — `docs/observability.md:27` 列事件仅 `move/product_*/hang/opencode`；**缺 control mode、launch/startup failure、queue scan/skip、retry/abort、board API/Hub error**
- 控制面 H3 — `scripts/chat_server/routers/agent_proxy.py:127-132, 150-155` 把 `httpx.ConnectError` 的 IP / errno 全量回前端；`scripts/chat_server/services/claude_session.py:826, 1097-1099` 同问题
- 控制面 H3 旁证 — `scripts/chat_server/routers/desktop.py:590-591, 800-801, 914-916` `payload["seed_warning"] = str(exc)[:200]` 把 `OSError`/`ValueError` 文本（含绝对路径）回给客户端
- 看板存储 — `scripts/_board_store.py:675-785` `list_tasks()` 损坏 JSON 行只 debug 日志跳过；**合法 JSON 但字段类型错误仍进入排序及业务逻辑**；`find_task()` 只读第一行，异常即把任务当不存在
- 看板存储 — `scripts/_board_store.py:787-825` 双副本时 `find_task` 按列顺序先命中，**读到的可能是旧副本**
- 执行器 M8 — `scripts/_jsonl_rotate.py:48-57` `failures.jsonl` 写失败 `pass`（失败账本本身写不进去）
- 控制面 M3 — `scripts/chat_server/auth.py:11-13` `_auth_failures` defaultdict 无上界；攻击者从随机 IP 发错密码 → 字典按 IP 增长

**根因**：错误传播链每一层都在"降级"或"静默"，最终 ops 看到的看板状态、upstream 状态、hang 状态全是**有偏样本**。

**业务后果**：看不到问题 → "问题不存在" — 这是稳定性最大的暗洞。

### 类别 ③：进程生命周期失控（**第三严重，影响日常运行**）

**子证据**：

- 调度核心 #1 — `scripts/ccc-engine.py:4400-4413` graceful shutdown 只设布尔标志；main 终止 `:4428-4444`；**不杀 product/OpenCode/reviewer/pytest 子进程**
- 调度核心 #2 — `scripts/ccc-engine.py:456-493` watchdog tick 超 180s 直接 `os._exit(0)`，跳过 finally/atexit/持久化；`scripts/engine/gates.py:620-634` testing gate 默认 180s 预算 — **watchdog 必自杀**
- 执行器 H1 — `scripts/_executor.py:273-282` `Popen` 后崩溃无清理；`finally` 只清 pid_file + tmp_path，子进程不回收
- 执行器 H2/H7 — `scripts/_executor.py:277-278`、`scripts/opencode-exec.py:220-223` `Popen(stdout=PIPE)` + `communicate()`；stdout/stderr 单边 > 64KB → 子进程阻塞 write → `communicate` 等读 → **死锁**；reviewer prompt 已实测 >1MB（`scripts/board/roles/reviewer.py:1097`）
- 执行器 H5 — `scripts/engine/hang.py:65-92` wall-clock vs activity mtime 混淆；in-process token 生成不算 IO 写盘，但 `_is_no_progress` 把 `started_ts` fallback 当 "since start"
- 控制面 H5 — `scripts/chat_server/app.py:49-54` `_lifespan` 只 `close_client()`，**未调用 `session_manager.shutdown()`**；Hub exit 时 ClaudeSDKClient / loop-code 子进程变孤儿
- 控制面 H6 — `scripts/install-hub-plist.sh:92-98` install 端口盲杀；bash 里 `kill $pids` **只 kill 第一个 PID**（`kill 1234 5678` 才全发）
- 执行器 L5 — `scripts/ccc-engine.py:4400-4444` Engine 退出时无 subprocess 收尾；launchd `SuccessfulExitTimeout=30` 延迟重启 30s 期间 hang 子进程仍在跑
- 执行器 M7/L1 — `scripts/_config.py:108` 默认 `xfyun/code`，`model_tiers["code"].fallback_providers`（`:184-187`）**无调用方读**；CLAUDE.md:255 写的 xfyun→zhipu fallback **无实现**

**根因**：每个 Popen 调用点都有自己的清理逻辑，行为漂移；没有统一的 `_kill_process_tree_pid`、没有统一的 preflight 心跳、没有统一的 shutdown 协议。

**业务后果**：用户在 stress/medium fanout 场景已经踩过（**Lesson 44、product 鉴权失败的 fd 12 case**）——这是已知爆雷。

### 类别 ④：门禁形同虚设（**第四严重，影响代码质量**）

**子证据**：

- 调度核心 #7 — `scripts/engine/gates.py:49-58, 459-475, 540-569` verdict 兼容逻辑允许"非空但无 Verdict 行"的旧文件继续，**判定可被绕过**
- 调度核心 #8 — `scripts/board/roles/reviewer.py:246-269, 1520-1536, 1646-1669` reviewer **可直接 testing→verified**；tester_role 遍历不到
- 调度核心 #9 — `scripts/board/roles/tester.py:415-603` + `scripts/engine/gates.py:499-569` tester 结果 Engine 不保存不检查，**只看 `verdict_ok`**
- 调度核心 #17 — `scripts/ccc-engine.py:3700-3721, 3724-3880` 异常默认全 transient，关键词宽（"失败/failed/quarantine/opencode"），auto-refeed 2 次叠加 phase/review/product/hang retry — **单卡最多 ~54 次重试**
- 调度核心 #18 — `scripts/board/roles/reviewer.py:1114-1147` reviewer 内 3 次重试（每次 `time.sleep(10)` 无指数退避） + `scripts/engine/gates.py:432-457` 外层 gate 又重试 reviewer — **嵌套重试**
- 调度核心 #19 — `scripts/engine/gates.py:682-766` gate timeout 按全系统命令行匹配 kill，claude 只要求含 `-p`，**未限定 workspace/task**，可能杀其它仓评审
- 调度核心 #21 — `scripts/engine/gates.py:92-133, 519-529` pytest 超时统一返回 exit1，无法区分 timeout 与真实失败
- E2E 漂绿 — `tests/e2e/test_green_pipeline_e2e.sh` 实际验证 "LLM unavailable→FALLBACK stay testing"，**不是 PASS→verified**
- 看板存储 — `references/board-task-schema.md:239-290` 协议文档公开鼓励 Python/Bash/Node 直接写 `.ccc/board`，**绕过 FileBoardStore 与锁**

**根因**：评审/测试结果未走单一权威路径，verdict schema 不严格，每个角色都能"自己说了算"。

**业务后果**：开发者以为"过了 tester"，实际 tester 没真正生效；LLM 失败被当成 transient 一直重试，成本不可控。

### 类别 ⑤：红线 12 实际无防护（**第五严重，安全相关**）

**子证据**：

- 控制面 H2 — `scripts/_ccc_control.py:134-211` 任何 `set_mode("enabled", source=任意字符串)` 都接受；`source` 字段仅元数据不参与策略
- 控制面 H2 旁证 — `scripts/chat_server/routers/board.py:150-221` 任何 transfer 都能 `ensure_engine_for_task` → `set_mode("enabled", source="task_dispatch")`
- 控制面 M9 — `scripts/install-hub-plist.sh:68-72, 107-108` plist 把 `CCC_CHAT_USER=ccc` / `CCC_CHAT_PASS=ccc` 写入 plist XML（文件 `0644` 可读）；`scripts/chat_server/config.py:272-277` `validate_auth_config` 只警告不退出
- 控制面 M9 — `scripts/chat_server/config.py:17` 默认 `0.0.0.0` 监听 → 同网段脚本可 Basic Auth 进 Hub
- 控制面 L8 — `scripts/chat_server/config.py:54-58`、`scripts/chat_server/app.py:67-74` CORS `allow_origin_regex` 允许 `10.x.x.x` + `allow_credentials=True` → 同网段恶意 SPA 可带 cookie
- 控制面 H1 — CLI 与 Hub 写 `~/.ccc/control.json` 无共享 flock
- 控制面 H3 — `agent_proxy` / `claude_session` 把内部 IP / errno 全量回前端
- 控制面+Hub 后端 L7 — `scripts/ccc-autostart-guard.sh:164-175` `_invent()` 仍能启动 engine（`set_mode("invent")` Python 端降级 enabled，shell 端继续 `_start_engine`）

**根因**：CLAUDE.md 红线 12 在当前代码实际只有"agent 不要主动 `set_mode('enabled')`"的**约定**，**技术防护 0 道**。

**业务后果**：Hub 暴露在 LAN 上时，任何同网段进程（含恶意脚本）能停 Engine、改写 control.json、读取失败账本。
