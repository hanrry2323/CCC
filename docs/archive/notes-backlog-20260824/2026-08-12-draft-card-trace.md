## 一、 「草案」栏卡片的定义、分栏与 UI 映射

### 1. 默认状态与新建规则
*   在 `server/board/plans.py` 中的 `create_plan` 方法内，当用户新建方案时，系统会在 Markdown 文件的头部元信息中默认注入：`状态：草案`。
*   所有的方案创建，默认初始状态全部固定为 **草案**。

### 2. 数据流与分栏过滤
*   **后端接口无分栏**：后端 `/plans/list` 接口（`_handle_plans_list` 端点）仅对文件进行全量扫描，并在 JSON 中以扁平的方案数组形式返回给客户端。
*   **前端纯客户端分栏**：分栏完全由前端 `plansPage.js` 实现。代码中使用 `filteredPlans().filter(p => p.status === status)`，在客户端根据每个方案的 `status` 字段，将其动态分流到看板的五个列（列即状态：`草案`、`已确认`、`部分执行`、`已完成`、`作废`）中。

### 3. UI 差异与子状态标记
*   **副标题（子状态）暗示**：在前端渲染时，「草案」栏的列头带有一个清晰的语义化副标题——**“待讨论”**。
    *   与之对比：`已确认` 的副标题为 “待排期”；`部分执行` 为 “已转卡”；`已完成` 为 “卡全关”；`作废` 为 “不执行”。
*   **视觉与交互**：
    *   **颜色**：草案卡片的左缘状态条采用灰褐色标识（`#a39e93`）。
    *   **动作锁定**：在草案状态下，卡片底部**不提供**「转为任务卡」等物理按钮（该按钮只有处于 `已确认` 或 `部分执行` 状态，且转卡计划不为空时才会展示）。

### 4. 状态机流转与契约
根据官方 `docs/DOC-PROTOCOL.md` §2.8 定义：
*   **草案语义**：**方案初稿，待讨论确认**。
*   **流转白名单限制**：草案作为生命周期的起点，在拖拽或下拉切换时，**只能**流转至 `已确认` 状态或直接 `作废`，禁止直接跨越到 `部分执行` 或 `已完成`。

## 四、 线路图 Epic 里程碑派生逻辑

在 `server/board/loader.py` 的 `derive_epic_states_and_progress` 函数中，线路图的 Epic 并不是一个拥有独立持久化数据库的独立对象，而是**基于卡片关联的单事实源（SSOT）动态计算出来的：**

1.  **里程碑模型**：依旧使用 `BoardItem` 数据结构，当其 `type == "epic"` 时视为史诗卡/里程碑。
2.  **进度推导**：
    *   在加载时，系统会扫描所有 `type == "task"` 且 `parent` 字段匹配此 Epic ID 的子卡。
    *   计算关闭率：`closed / total`（子卡在 `cards.index.jsonl` 索引中的状态 `base_state` 为 `已关闭` 时计算为 done）。
    *   **标题级联覆盖**：推导出的进度会被动态拼接入卡片标题返回给前端渲染，例如：`"里程碑 A (3/5)"`。
3.  **状态推导**：
    *   若子卡全部关闭 (`closed == total`)：里程碑状态派生为 **`已回写`** (表示已交付，待合入)。
    *   若尚有子卡在途 (状态含 `执行中`, `已回写`, `打回`)：里程碑状态派生为 **`执行中`**。
    *   若子卡均未启动：里程碑状态派生为 **`待分派`**。
