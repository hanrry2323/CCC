### 各环节详细说明

#### [1] 出卡（人工）
- **入口**：`scripts/new-card.sh`（单卡）/ `scripts/plan-to-cards.sh`（多卡）
- **命名**：`docs/dispatch/<prefix>/<prefix><NNN>-<slug>.md`
- **分支**：`codex/<stem>`
- **校验**：`python3 -m server.board.validate docs/dispatch`
- **当前状态**：模板化基本完成，但仍是人工触发。方案→卡需人工点「转为任务卡」。

#### [2] 派发（Engine 自动）
- **核心函数**：`run_once()` → 扫 `State.TODO` 卡 → `decide_work()` 决策
- **决策四态**：
  - `AUTO`：可后台 CLI + transport=local → Engine 本机 spawn（`subprocess.Popen`）
  - `REMOTE`：Worker 号 + transport=git → 远端认领（不占槽、不本地拉起）
  - `MANUAL`：手动 GUI / 派发=manual → 挂起等人
  - `NONE`：管理席/验收席/未知 → 不派发
- **并发控制**：`DispatchPool`（线程池）+ 槽位上限 `max_concurrent`
- **业务仓隔离**（2026-08-12 新增）：同仓最多 `isolation_max_concurrent` 张卡并发
- **防呆**：父卡未关闭不派发、依赖未关闭不派发、依赖环检测、已验收卡不派发
- **心跳**：持续模式每 60s 一轮

#### [3] 执行（Worker 自动）
- **AUTO 卡**：Engine 在 worktree 中 spawn OpenCode/Claude Code
  - 读卡 → 按白名单开发 → 回写卡头 → `git push origin <branch>` → exit 0
  - 超时：`EXECUTOR_TIMEOUT_SECONDS`（默认 300s）
  - 基础设施故障：不进重试预算，冷却后自动续跑（指数退避）
- **REMOTE 卡**：远端 Worker 通过 `scripts/worker-claim.sh` 认领
  - pull → 找待认领卡 → 写认领标记 → 执行 → 回写 → push
  - Engine 侧 `_claim_round()` 收单：认领+已回写→收单；认领超时→回收
- **业务仓 worktree**（2026-08-12 新增）：每卡独立 worktree 在 `<隔离根>/<work_id>`

#### [4] 机审（Engine 自动）
- **核心函数**：`_audit_round()` → 扫 `State.DONE`（已回写）卡
- **验收席**：由验收席 CLI（Claude Code）执行机审
  - 检查：代码 review、安全扫描、文档完整性、维护区四问
  - 写 `## 机审区` 到卡文件
- **结果**：通过 → 标「机审：通过」；不通过 → 打回待分派（重试）或打回（重试用尽）
- **机审钉**：记录被审 commit SHA，合入时校验无漂移
- **防死循环**（2026-08-12 修复）：机审打回时同步落分支卡状态，防止信封残留「已回写」→ 无限机审

#### [5] 合入批准（人工 — 老板唯一动作）
- **入口**：`scripts/approve-merge.sh <card-id>` 或 `--ready`（批处理）
- **门禁链**：
  1. 机审通过（分支信封/本地卡含「机审：通过」）
  2. 机审钉无漂移（被审 SHA 之后只有卡文件改动）
  3. 维护区四问已完成（Doc-Gate 机械门禁）
  4. 跨仓收口：业务仓分支 ff-merge 到业务 main + 删分支
  5. CCC 仓：ff-merge 或 close-only
  6. 写验收区 + 状态→已关闭
  7. 清除 sidecar 流程态
  8. 触发 2017 部署检查
- **ready 队列**：`/board/ready_for_merge`（扫描所有 origin/codex/* 分支中机审通过且未合入的卡）

#### [6] 部署检查（approve-merge 自动触发）
- 检查 2017 生产 vs origin/main 是否一致
- 落后 → 自动 `deploy-ccc.sh`（pull + 服务 kickstart + 健康检查）
- 支持本地/SSH 两种路径

#### [7] Loop 巡查（Scheduler 定时）
- **框架**：`server/engine/scheduler.py`（通用定时任务框架）
- **Observer**：`server/engine/observer.py`
  - 只读巡检：治理一致性、依赖环检测、卡状态异常
  - 逆向巡查：交叉验证
  - 指标采集：Playwright 功能巡查
- **任务类型**：readonly（采集不动作）、change（生成任务卡）

## 三、瓶颈与痛点（按严重程度排序）

### P0 — 阻塞性

**1. 合入批准是单点人工瓶颈**

- **现状**：老板是唯一合入批准人。机审通过后仍需人工执行 `approve-merge.sh`。
- **证据**：2026-08-12 批量补办 58 张 hp/qb/xy 旧卡验收区——这些卡机审早已通过、代码早已在 main，但因为没有「合入批准」动作而卡在 ready 队列。
- **影响**：产线吞吐量受限于老板的 availability。58 张卡可以一次性批量代批，但这不是常态——正常流程要求逐张审 diff。
- **根因**：流程设计上「合入批准」是北星 W2 的人审节点，没有自动化路径。

**2. 机审打回→死循环风险（已修复但需持续警惕）**

- **已修复**：mx031/032 假机审根因（2026-08-12）——机审打回未同步改分支卡状态，信封残留「已回写」→ 下轮又读成 DONE → 无限机审。
- **修复方案**：`_mark_branch_card_state()` 打回时同步落分支卡状态。
- **风险**：类似的双源漂移问题可能在 REMOTE 卡认领协议中重演（sidecar vs 磁盘卡 vs 分支信封三源）。

### P1 — 严重

**3. 集群 Worker 池未真正运转**

- **现状**：Worker 模型 + 认领协议代码已落地（ccc-plan-020 A 轨第 2 项），但 252 未配置 daemon。
- **证据**：`worker-claim.sh` 已就位，但 252 上无 cron/launchd 定期跑认领。clw020 类 REMOTE 卡无法真正跨节点执行。
- **影响**：集群 Worker 池只有 2017 一个节点实际工作，扩展性为零。

**4. 252 实跑闭环未完成**

- SSH banner 超时（客观网络阻塞），等网络修复或 252 本机操作。
- 集群并发扩展验证未做（2017+252 同时执行不同卡）。
- 认领冲突 CAS 未实现——两 Worker 同时认领同卡无原子保护。

**5. 100 卡基线计划未闭环**

- 计划 8/8-8/10 完成 100 卡，50 卡验收点做架构修正。
- 架构修正已完成（A 轨四项），但修正后效果未验证（后 50 卡未跑）。
- 循环健康指标（时长/调用/打回率/机审延迟）未可视化。

### P2 — 中等

**6. 交付闸门（Delivery Gate）未完成**

- ccc-plan-017 状态=部分执行。两张卡（§7 交付收尾 + validate-plans.sh 方案级校验）未落地。
- 13 个方案「卡全关未收尾」仍未处理。
- 项目级交付收尾无 SOP，只有单卡级 Doc-Gate。

**7. 机审远程适配不完整**

- remote 卡机审仍需要 2017 验收席 CLI 拉起。
- 无本地 worktree 时机审走分支信封读证据，但机审 agent 本身未分布式化。

**8. 看板无实时推送**

- 依赖 12s 轮询（`board.js` 静态导出由 board-scheduler 定时刷新）。
- SSE 推送列入 T49/T50 但未实现。

### P3 — 低优先级

**9. 注册表双源漂移**

- `executors.example.json` 与 `2017 生产 executors.json` 不一致。
- W1-W4 transport 字段 example 未同步补。

**10. 出卡模板化未完全自动化**

- 意图→出卡仍需人工对话收敛。
- 「自动任务发现」列在四大差距中，未启动。

**11. skill 全量收仓未覆盖 252**

- SSOT 6 skill 已进仓，但 252 节点 skill 目录未配置。
- sync-skills 无自动定时（需节点 cron/daemon）。

## 四、优化机会清单（具体可执行）

### 高杠杆（投入小、收益大）

1. **合入批准半自动化**
   - 机审通过 + 维护区四问完成 + 无漂移 → 自动进入「待合入」队列
   - 老板只需确认（一键批处理），不需要逐张执行
   - 实现：`approve-merge.sh --auto` 模式，跳过人工 diff 审查（机审已做）
   - 风险控制：首批只对「代码未改动」类卡（如文档卡、配置卡）开放自动合入

2. **252 Worker daemon 部署**
   - 命令已就绪：`worker-claim.sh --claim-only` + 执行器
   - 252 配 cron/launchd 定期跑（每 60s）
   - 第一个 REMOTE 卡跨节点闭环后，集群模式即可验证

3. **循环健康指标看板化**
   - 数据已采集（ProcessSampler、metrics.py），只需可视化
   - 展示：每卡平均时长、工具调用次数、打回率、机审延迟、槽位利用率
   - 挂在看板 `/board/metrics`

### 中杠杆

4. **交付闸门落地**
   - 完成 ccc-plan-017 两张卡：onboarding §7 + validate-plans.sh 方案级校验
   - 处理 13 个「卡全关未收尾」方案
   - CLW 作为第一个交付实例走示范

5. **看板 SSE 实时推送**
   - 替代 12s 轮询，Engine 状态变更时主动推送
   - 对话右栏卡流、看板均可受益

6. **出卡自动发现**
   - 从 backlog/意图自动拆卡排序（四大差距 #2）
   - 先做简单的：老板说「把 X 做了」→ 自动拆成卡草案 → 老板确认

### 低杠杆（长期）

7. **认领冲突 CAS 原子化**
   - 并发 Worker 池扩展前补（git lock marker 原子操作）

8. **机审分布式化**
   - remote 卡机审可由远端 Worker 本地执行（而非回 2017 审）

9. **全自动合入（远期）**
   - 机审 + 维护区 + 无漂移 + 测试全绿 → 全自动合入
   - 需要极高的机审准确率和测试覆盖率

## 七、总结

CCC 自动开发流程的**核心链路（派发→执行→机审）已全自动**，运转良好。A 轨四项（sidecar 契约/Worker 模型/机审打回可执行性/role-skills 一致性）已完成平台根治。

**最大的瓶颈是合入批准**——这是流程中唯一不可绕过的人工节点。58 张卡批量补办暴露了这个问题：机审和代码都在，但缺「合入批准」动作就卡住。

**第二瓶颈是集群 Worker 池未真正运转**——代码已就绪，但 252 未接入，无法验证跨节点扩展。

**建议优先级**：
1. 252 daemon 部署（打通第一个跨节点闭环）
2. 合入批准半自动化（机审通过+维护区完成 → 一键批处理）
3. 循环健康指标看板化（数据已有，可视化即可）
4. 交付闸门落地（两张卡，消除方案级收尾盲区）
