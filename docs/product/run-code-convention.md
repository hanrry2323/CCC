# Run Code 执行模式约定（CCC 执行层）

> 吸收自 DeepSeek Harness 的 Run Code 模式（2026-08-15，ccc-plan-029 卡1）。
> 目的：执行体处理复杂 JSON/Markdown 元数据或文本改动时，用**内存临时脚本**替代 sed/awk 拼装——快、稳、语义正确、项目零残留。

## 一、什么场景用

| 场景 | 推荐 | 理由 |
|------|------|------|
| JSON / YAML 嵌套结构批量改（按条件改字段） | ✅ 内存脚本 | sed 全局替换易产生**语义错误**（如把冷冻节点端口误改成新值） |
| Markdown 表格 / 多文件一致性编辑 | ✅ 内存脚本 | 结构感知，一次到位 |
| 简单单串替换（版本号、单一字面量） | sed 亦可 | 无嵌套逻辑，sed 足够 |
| 长驻服务 / 交互程序 | ❌ 均不适用 | 交给 Engine 派发，不用内联脚本 |

## 二、怎么用

```bash
# 辅助脚本：scripts/ccc-run-inline（内存执行，临时目录自动清理）
ccc-run-inline node 'const d=JSON.parse(fs.readFileSync(process.env.CCC_PROJECT_DIR+"/x.json")); ...'
ccc-run-inline py   'import json; ...'
echo '<code>' | ccc-run-inline node --timeout 10   # stdin 读代码

# 项目目录经 CCC_PROJECT_DIR 暴露，脚本可读写目标文件；脚本自身在临时目录运行，零残留
```

## 三、纪律（硬）

1. **语义优先**：按业务逻辑写变换（条件/分支/遍历），不做全局盲替换——Demo 证明 sed 会把"冷冻节点端口"误改成活端口。
2. **零残留**：脚本的临时文件在临时目录、自动清理；只允许对目标文件做有意的修改，不落任何中间文件。
3. **有界**：`--timeout` 设上限（默认 30s），超时终止；不跑长驻/交互。
4. **真实反馈**：脚本输出必须打印关键变换结果（如改后 JSON 摘要），便于复核——不静默。

## 四、为什么（背景）

- DSH Run Code = 模型写 TS 脚本、内存执行、真实反馈、零残留；实测在多步探测/复杂变换上比"模型逐步发命令"快且准。
- CCC 执行层吸收的是这个**执行模式**（模型无关），不是 DSH 的模型或框架——模型的谄媚/断言缺陷用指令纪律与模型选型管住，不混入架构层。

## 五、任务级 CodeRun 编排（编排范式）

> 上面一~四章是**工具级** Run Code（单条命令用内存脚本）。本章是**任务级** CodeRun 编排——agent 面对一个多步骤任务时，用「写编排脚本一次编排」而非「逐轮敲命令」。实证：2026-08-17 Minecraft 首单（`experiments/dsh-eval/notes/33`），opencode 收转译指令后产出 557 行单体编排脚本、2.7 分钟全流程、1 轮收敛。

### 5.1 什么任务用（场景表）

| 任务形态 | 是否走编排 | 理由 |
|------|------|------|
| 多步骤任务（取证→实现→验证→部署） | ✅ 编排脚本 | 一次编排，非逐轮往返；Minecraft 实证收敛快 |
| 多服务 / 多文件并行取证 | ✅ 脚本内并发 | 并行取证一次拿全貌（hp030 三态探针） |
| 单文件简单改动 | ❌ 常规逐轮 | 编排是微开销，无收益 |
| 交互 / 长驻程序 | ❌ 不适用 | 交给 Engine 派发 |

### 5.2 可执行转译指令（标准段落，写卡人按需贴入任务卡）

> **术语转译教训（硬）**：OpenCode / Claude Code 不认「CodeRun」「cc-run-inline 式」「curated result」等 DSH 术语。触发编排必须用**可执行动词**，禁用术语。以下为唯一标准表述，贴入任务卡即可生效：

```
本任务要求 CodeRun 编排：
1. 写编排脚本：多步骤工作写成一个编排脚本（bash/python）一次编排完成，而非逐轮敲命令。
2. 完整文件一次生成：能一次生成的完整文件用 heredoc/一次写入，不拆分多次编辑。
3. 并行取证：需并行的步骤（多服务探测/多文件取证）在脚本内并发。
4. 自检：编排脚本必须自带产物自校验（HTTP 200 / 单测 / 输出摘要），失败 exit 非零。
5. 交付：最终交付含编排脚本 + 验证证据。
```

### 5.3 机审遵守度检查（机审席验证项）

任务卡含 5.2 段落时，机审席须检查：
- **编排脚本存在**：产物里能看到编排脚本（如 setup_and_deploy.sh 式），而非只有散落的逐个命令记录；
- **完整文件一次生成**：主产物是脚本一次写出的（heredoc/单次写入），不是 N 次 edit 拼装；
- **自检证据**：编排脚本自带自校验输出（HTTP 200 / 单测 / 摘要）。
- 逐轮散调（每步单独敲一次工具）且无编排脚本 → 视为未遵守，打回。

### 5.4 为什么（Minecraft 实证 2026-08-17）

- 转译指令下发后 opencode 完整遵守：`setup_and_deploy.sh` 一次编排 生成→端口处理→起服务→curl 200 自检，2.7 分钟 / 1 轮迭代收敛。
- 编排自检发现不了交互 bug（pointer-events 挡点击）——**机审/人工复测环节不可省**，编排只省开发往返，不替代验收。
