# 机审 SOP（立即审 · 单卡质量）

> **定位**：机审是「立即审」——审查本次开发的代码质量、是否破红线、规范符合度。判的是这次改动好不好，AI 可稳定判定。
> **与审核/Loop 关系**：机审（单卡立即审）→ 审核（阶段整体验收）→ Loop（后台持续审）。三层分工，机审最窄最硬。
> **依据**：ENGINEERING-CANON §二（验收体系）+ 2026-08-11 老板定调。
> **状态**：v1 定稿 · 更新：2026-08-11

---

## 一、机审职责（窄而硬）

机审只判**可判定的硬标准**：
1. 代码质量（逻辑正确、异常处理、架构合理）
2. 红线（越界、意图违背、安全漏洞）
3. 规范符合度（命名、结构、Doc-Gate 维护区四问）
4. 声明真实性（回写声明引用的工件真实存在且与卡改动一致）

**机审不判主观**：主观标准（美观/体验/设计品味）不归任何 Agent 判定——Agent 没有主观。主观只存在于人的意图层，通过老板↔IDE 工具对话表达，由人判断（意图开发核心）。机审、审核、Loop 三层都只处理可判定的硬标准。

---

## 二、四类判定（机审行为边界）

| 判定 | 机审行为 | 依据 |
|------|---------|------|
| **红线**（范围系统性越界/核心业务意图违背/安全漏洞） | **必须打回**，附可执行原因 | 红线一票否决 |
| **可修问题**（命名/注释/小重构/补测试） | **就地修复** → commit+push → 修完直接通过，**不重走开发** | 修补有界 |
| **机械失败**（编译/测试/lint/范围） | 归门禁裁决，**不进机审**（机审不重复检查） | 门禁底线 |
| **主观标准**（美观/体验） | **不判**——主观只在人的意图层，由老板/IDE 对话判断，不进 Agent 判定链 | 意图开发核心 |

---

## 三、打回原因可执行性（硬要求）

**打回原因必须可执行**：`问题 → 文件:行号 + 唯一最佳动作`。

- ✅ 可执行：`GitBadge.tsx:30 引用 --warning-color 未定义 → 在主题 token 中定义或改用现有变量`
- ❌ 不可执行：`体验不好` / `代码不规范` / `需改进`（执行体无法确定怎么修，必然重试撞墙）

**为什么**：死循环的根因不是"限制多"，是"标准不可判定"。可执行原因 = 执行体一次能修对，不重试。

---

## 四、防死循环三柱（机审侧）

1. **标准可判定**：机审只留硬标准（§一），主观标准移出
2. **修补有界**：可修问题就地修（不重走开发）；红线才打回重做；机械失败归门禁
3. **重试有上限**：retry 上限 3 次，用尽打回待人工，不无限循环

---

## 五、机审输出格式

```
机审：通过（被审 <sha12>）          ← 通过（含钉 commit）
机审：通过
机审：不通过（<可执行原因：文件:行号 + 唯一最佳动作>）  ← 打回（原因必须可执行）
机审：不通过（维护区未完成：<缺失项>）
机审：不通过（维护区声明不实：<工件> <实际> <应然>）
```

**红线**：
1. 打回原因禁止"体验/美观/主观"表述
2. 不通过必须给出执行体能直接照做的修复路径
3. 机械失败（编译/测试/lint）不写进机审不通过原因

---

## 六、与审核/Loop 的边界

| 环节 | 时机 | 审什么 | 谁判 | 输出 |
|------|------|--------|------|------|
| **机审** | 单卡回写后 | 本次质量/红线/规范 | LLM（异席） | 通过/打回 |
| **审核** | 阶段结束/版本前 | 整体一致性/回归/交付物 | 老板/验收席 | 阶段验收报告 |
| **Loop** | 后台持续 | 已回写项目 vs 线路图/文档漂移 | Loop Agent（只审不投） | 运维看板卡 |

> 主观标准（美观/体验）不归 Agent 判定（机审/审核/Loop 都只判硬标准）——主观只在人的意图层，通过老板↔IDE 对话表达与判断（意图开发核心）。
