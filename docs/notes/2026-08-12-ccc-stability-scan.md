# CCC 稳定性薄弱点清单

> 日期：2026-08-12 · 调研员：OpenCode · 调研对象：CCC 核心系统与脚本

---

## 一、 核心薄弱点清单 (按严重程度排序)

### 1. 【P0 级】三源状态真值漂移与无锁认领 (架构风险)
*   **位置**：`store.py:_branch_envelope_state` + `main.py:_audit_round` + `runtime_state.py`
*   **影响面**：当并发启动多个引擎、或者远端 Worker (M1 与 2017) 共同认领任务时，由于**分支信封、磁盘卡、Sidecar 本地文件**这三种状态源之间缺乏原子锁（CAS），会发生状态双写冲突，导致同一张卡在机审和分派之间死循环，或同一张卡被重复分派、认领死锁。
*   **当前兜底**：通过事后对账补漏机制（`converger` 收敛器和反向写分支补丁）进行“治标”纠偏，无法从源头预防。
*   **加固建议**：
    1. 统一状态权威，将 **分支信封（远端最新快照）** 定为唯一真值。
    2. 在 `worker-claim.sh` 阶段利用 Git push 远端的原子性实现 CAS（Compare-And-Swap）认领互斥锁，抢占失败则安全回滚。

### 2. 【P1 级】定时任务框架串行裸奔与无 try-except 保护 (重大设计盲区)
*   **位置**：`server/engine/scheduler.py`
*   **影响面**：`server/engine/scheduler.py` 中的所有巡检与变更任务均为**单线程串行同步执行**，且没有对单个任务添加 `try...except` 保护。若其中一个任务（如 Playwright 指标采集或 SSH 探活）由于网络问题超时挂起（hang），或者抛出未捕获异常，将**拖死整个调度主循环，导致整个定时框架直接崩溃退出**。
*   **当前兜底**：无。完全裸奔。
*   **加固建议**：
    1. 在 `run_tasks` 中对每个 `task.run(cfg)` 的调用外层包裹 `try...except Exception:`，确保单点故障不拖垮整个调度器。
    2. 引入线程池隔离，并给巡检任务设定硬性执行超时阈值（如 60 秒），超时强制回收。

### 3. 【P1 级】`approve-merge.sh` 证据链本地回退后门 (安全防线漏洞)
*   **位置**：`approve-merge.sh` 第 366-379 行
*   **影响面**：合入前本应强制校验 `origin/codex` 远端分支信封上的“机审通过”标记。但脚本在未找到远端证据时，开辟了“回退读取本地磁盘卡”的后门。若本地磁盘卡被意外脏改，将发生**未通过机审的代码直接被合入生产 main 的严重事故**。
*   **当前兜底**：无。
*   **加固建议**：在 `approve-merge.sh` 中移除对本地磁盘卡的回退逻辑，强制“只认分支信封”；仅在显式指定人工豁免的 `--close-only` 文档卡时允许本地核对，并报出黄色警告。

### 4. 【P1 级】执行体 (Claude/OpenCode) PID 溢出与僵尸进程残留 (资源泄露)
*   **位置**：`server/engine/main.py`
*   **影响面**：引擎在执行超时或遇到故障强杀子进程时，或者 Engine 重启与子进程父子链接断裂时，子进程虽然在 Sidecar 中被剔除占槽，但在宿主机上极易演变成**孤儿僵尸进程**，长期运行会耗尽系统内存与 PTY 句柄。
*   **当前兜底**：有 PID 活性标记检测，但只清理标记，不主动清理残留的操作系统孤儿进程本身。
*   **加固建议**：在重放或清理孤儿标记时，若通过 `ps` 查到我们派发的 `opencode`/`claude` 依然存活，强制发送 `SIGKILL` 物理清洗；使用 `setsid` 建立独立进程组并用 `killpg` 整体强杀。

### 5. 【P2 级】核心脚本与代码中大范围硬编码双机路径与内网 IP (跨机失效)
*   **位置**：`approve-merge.sh`、`observer.py`、`card-evidence.sh`、`validate-plans.sh` 
*   **影响面**：在 `/Users/fan/...`、`192.168.3.116` 等 2017 主机的特定路径与 IP 绑死，且脚本内存在直接使用 naked `python3`（绕过环境指定的 `$CCC_PYTHON_BIN`）的情况。在 M1 主机（`Users/apple`）上运行时会导致大量脚本报错，需要反复打特定补丁兼容。
*   **当前兜底**：遇到报错后，临时在 git commit 中打双机路径对齐补丁，属于被动维护。
*   **加固建议**：
    1. 将一切绝对路径、SSH 节点、内网 IP 彻底抽取为环境变量，写在 `config.env` 中进行注入。
    2. 增加代码门禁静态扫描，拦截任何包含私有 IP 和特定主机绝对路径的源码修改。

## 二、 测试覆盖弱点分析

通过 pytest 收集到全案 830 个测试，测试集对逻辑控制与并发槽处理具有很强的防守能力，但在以下线上场景测试极度薄弱：

1.  **调度器卡死与退避测试**：完全缺失。未曾针对 Scheduler 中任务执行异常、无响应挂起时的保护和自我修复进行过集成测试。
2.  **网络故障与 Git 锁冲突模拟**：极少。在 multi-branch 协同 sync、SSH 网络高延迟探活失败、多 Worker 抢占 Git 锁发生冲突等极端外界物理异常下，缺少测试端点的 mock 覆盖。

---

## 三、 调研结论

**结论：CCC 核心业务开发链路运转高度自动化，当前主要稳定性瓶颈已从开发逻辑转移至真值管理与配置隔离，通过立即收紧本地合入后门、隔离加固定时任务框架、并为 Worker 认领机制引入原子锁，即可将大部分线上崩溃与漂移隐患消灭在萌芽状态。**
