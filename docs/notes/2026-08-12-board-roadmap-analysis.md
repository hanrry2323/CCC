## 一、 线路图与方案池数据模型

在 CCC 平台中，方案（Plan）与任务卡是彼此独立但又通过引用相互绑定的两个实体。

### 1. Plan 实体模型
*   **物理载体**：存储于 `docs/projects/<prefix>/plans/<NNN>-<slug>.md`，完全以 Markdown 文件形式落盘。
*   **数据结构**：后端通过 `server/board/plans.py`，利用正则表达式对 Markdown 头部元数据行、一级标题、`## 验收标准` 的 checkbox、以及 `## 转卡计划` 正文段进行动态解析，封装成 dict 对象：
    *   `id`: `{prefix}-plan-{num}`
    *   `project`: 项目前缀（需在 `registry.yaml` 中注册）
    *   `num`: 三位序列号（如 `001`，同前缀下自增）
    *   `slug`: 标题转换后的连字符格式
    *   `title`: 去掉 `方案 · ` 前缀的一级标题
    *   `status`: 状态机五态之一
    *   `cards`: 关联任务卡列表，逗号分隔，如 `xy021, xy022`
    *   `acceptance`: 验收标准达成度，返回 `{"total": 5, "done": 2}`
    *   `path`: 相对路径

### 2. 状态机与生命周期
状态流转严格遵循 `VALID_STATES` 白名单（`草案 → 已确认 → 部分执行 → 已完成 → 作废`）：
*   **草案**：方案编写、讨论期。
*   **已确认**：讨论通过，等待排期。
*   **部分执行**：由人触发「转为任务卡」时，系统拉起 `new-card.sh` 批量在 `docs/dispatch/<prefix>/` 下生成具体的任务卡。生成成功后，状态**自动单向推进**到「部分执行」，并将这些卡号反向写回到 Markdown 卡头的 `> 关联卡：`。
*   **已完成**：属于终态。当所有的关联卡片在看板中变为「已关闭」状态时，由人或脚本将状态流转为已完成（终态不可再退回）。
*   **作废**：不删除文件，仅作为历史归档封存。

## 二、 当前渲染逻辑与端到端数据流

系统的整个数据链路采取 **Markdown Markdown-Database（缓存索引） ⇄ HTTP API ⇄ 前端视图** 架构，实现了轻量化与高可用：

```text
 ┌────────────────┐            lsof 扫描            ┌───────────────┐
 │ 2017 生产环境  ├────────────────────────────────▶│  /ops/ports   │
 └────────────────┘                                 └───────┬───────┘
                                                            │
 ┌────────────────┐         load_dispatch_cards             │
 │ docs/dispatch/ │───────────────┬─────────────────────────┼───────▶ 前端 SPA 看板
 └────────────────┘               │ (增量索引)               │          (#/plans)
                                  ▼                         │          (#/board)
 ┌────────────────┐      cards.index.jsonl                  │          (#/roadmap)
 │ docs/projects/ │───────────────┴─────────────────────────┼───────▶
 └────────────────┘          /plans/card-states             │
```

### 1. 后端接口提供
*   `GET /plans/list`：读取 `docs/projects/` 所有项目的 plans 目录。
*   `GET /plans/card-states`：**热路径高杠杆端点**。提取每个方案中绑定的卡 ID，再在 `cards.index.jsonl` 中查找这些卡当前所属的看板列（六列：待分派、执行中、机审、已回写、打回、已关闭），将分布计数一次性返回给前端。
*   `POST /plans/convert`：并发文件锁（`flock`）防呆，解析 `## 转卡计划` 内容并批量调用 `new-card.sh`，成功后自动 commit + push 到远端。

### 2. 前端 80+ 分 UI 升级体现
按方案 `023/024` 的要求，前端已完成了对四大页面的 80 分精致升级：
*   **计划页**：网格布局卡片尺寸统一等宽等高（152px），通过 CSS 截断避免文字遮挡。使用语义化标签（计划/缺口/警示）替代底层机器 ID 标签；项目切换禁用动画、锁定位置，做到零布局漂移。
*   **线路图二级页**：左侧保留垂直时间线，右侧面板引入按状态分组折叠，分类信息层次更丰富。
*   **运维页**：职责完全校正，系统状态移交控制台。专门按项目聚合「项目健康卡」、「工程化待办（diff 审核与异常发现）」以及「螺旋开发进度条」。
*   **看板页**：对已关闭列实现一键折叠，卡片按信息层级（舒适/紧凑）展示，加持了搜索和工具栏汇总。

## 三、 三层金字塔的实际实现情况

CCC 团队所设想的 **“线路图 → 计划池 → 看板”** 黄金三层金字塔，已经在当前的版本中得到了完整的逻辑与数据映射：

1.  **顶层：线路图（Roadmap / 骨架）**：
    *   通过 `registry.yaml` 读取所有注册的业务大项（如 xy, hp, mx）。
    *   通过 `loader.py` 中的 `derive_epic_states_and_progress`，扫描类型为 `epic` 的任务卡，抓取其 parent 包含的子卡，自动推导出 `closed/total` 进度，并将进度百分比、进行中、风险点以总览级呈现。
2.  **中层：计划池（Plans / 方案池）**：
    *   方案池是所有开发需求的创意源泉。编写方案须遵从 DOC-PROTOCOL 围栏约束，禁止散落在 notes。
    *   转卡机制是连接中层与底层的实体桥梁，起到了 **“共识到物理执行”** 的转承作用。
3.  **底层：看板（Board / 执行）**：
    *   代表实际在途的开发微任务卡，六列生命周期，由 Engine、Worker 及机审席自动轮转，最终老板执行 `approve-merge.sh` 实行最高合入闭环。

**现状评价**：金字塔结构已经物理打通。方案可以顺利转卡，卡片状态可以反向实时聚合为方案上的迷你流程图（流程条）。

## 四、 当前架构痛点与缺陷

尽管升级已达 80 分以上，但底层数据模型和流转逻辑仍暴露出 4 个系统性缺陷：

### 1. 【状态管理】方案“已完成”状态依赖人工回写，未与子卡全关状态强对账
*   **问题**：即使 `/plans/card-states` 算出了某方案下关联的所有卡片均已处于 `已关闭` 状态（即在途计数为 0，关闭计数达 100%），该方案文件头部 `状态：部分执行` 依然是静态的文本。
*   **后果**：会造成方案真实完成情况与表面状态文字的“时间差不一致”，只能依靠人工在前端详情页点改状态，或者等事后 `validate-plans` 巡检报警，缺乏后端自动化触发的“已完成”强核对和强制推荐动作。

### 2. 【数据流】`## 转卡计划` 段落的按行分割逻辑容易被格式细节脏污
*   **问题**：转卡解析时，采取了简单的逐行提取非 `#` 行、然后正则替换掉 markdown `[-*\d]` 符号的方案。
*   **后果**：如果方案编写者在 `## 转卡计划` 区域内写了多行备注、空行、或者换行说明，转卡解析器会因健壮性不足将这些普通行**误判成独立的任务卡**，导致在 dispatch 目录下产生大量的“卡名乱码”垃圾卡片。

### 3. 【状态漂移】`docs/roadmap.md` 人工挂账区依然采用半静态文档，未被后端完全数据化
*   **问题**：线路图一级的“产品北星下一程挂账”是产品方向的真值。目前 `docs/roadmap.md` 仅作为纯文本展示，无法被后端结构化，导致前端无法将“挂账意向”与“方案草案”进行自动的交叉比对。
*   **后果**：挂账条目容易在多人开发中遗忘。

### 4. 【流程韧性】转卡时 Git Push 失败处于 `partial: true` 后的回滚或重试机制缺失
*   **问题**：当 `_convert_plan_locked` 创建了全部卡并修改了方案状态后，最后一步会进行 `git commit && git push`。一旦因为网络原因 push 失败，虽然返回了 error 并报 `partial` 标志，但系统本地已经完成了修改且卡文件已落盘，系统无法提供优雅的一键“重新推送”或“事务回滚”。

## 五、 重构建议 (按优先级排序)

为了实现从 80 分向 90 分（高弹性、自愈性、零漂移）跨越，建议按以下优先级对看板和线路图模块进行加固：

### 1. 【高收益】 增强「转卡计划」Markdown 解析健壮性并提供转卡前览接口
*   **动作**：
    1. 在 `plans.py` 中重写转卡段提取逻辑，强制要求子卡标题行必须是 Markdown 列表行（即以 `-`、`*`、`1.` 开头），非列表行（如注释、纯说明）作为描述忽略，不作为新卡。
    2. 新增一个 `GET /plans/convert-preview?path=...` 只读接口，供前端在转卡前将解析到的“即将转出的 N 张卡片列表和标题”在弹窗中进行预览确认，防止误读。

### 2. 【高收益】 后端在 `/plans/list` 和巡检任务中，对“卡已关但状态未完成”的方案提供状态校准推荐
*   **动作**：在 `list_plans` 读取中，如果方案状态是 `部分执行`，但通过关联卡计数发现所有子卡都已关闭（且关联卡总数 > 0），在返回的元数据中加入 `recommend_status_complete: true` 标记。前端据此在卡片上高亮提示用户「关联卡已全部合入，建议一键完成」，由人确定点按改写状态，保证人工合入闭环红线的前提下，消除双源数据状态不一致的痛点。

### 3. 【中收益】 消除 `new-card.sh` 和 `validate-plans` 的 naked `python3` 调用，彻底实现解释器注入
*   **动作**：全面搜索 `plans.py` 中的 `subprocess.run` 和 `scheduler.py`，确保不通过 bare `python3` 调用任何校验与脚本。在运行子进程时，一律动态注入 `$CCC_PYTHON_BIN` 环境变量或者从 Python `sys.executable` 路径继承，解决在 M1 环境下运行外部环境缺失的问题。

### 4. 【中收益】 完善 `roadmap.md`「下一程挂账」的半自动解析
*   **动作**：在后端提供 `GET /roadmap/backlog` 接口，结构化解析 `docs/roadmap.md` 里的表格行。将下一程挂账表格转化为 JSON 格式。前端线路图页面可以直接渲染这些“挂账项”，并提供「直接创建对应项目方案」的接线动作，彻底形成：**线路图挂账 → 对应创建方案 → 方案转卡 → 看板执行** 的完全闭环。
