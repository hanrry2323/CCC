# CCC 教训 · 2026-08-25 · 工具新增非零退出语义必须同步审计调用方回滚契约

- 来源卡：ccc090（new-card.sh 出卡原子化）第 1 轮机审 F1（severity=中，打回）+ 第 2 轮复核。
- 现象：new-card.sh 新增「写卡成功后自动 add/commit/push」原子段并定义退出码 5=add 失败 / 6=commit 异常 / 7=push 失败或分支不可判定。但两个既有调用方都持有「rc≠0 ⇒ 无卡」的隐含契约：`server/board/plans.py` `convert_plan` 对任意 returncode≠0 执行 `_rollback_created()`（纯 `p.unlink`），`scripts/plan-to-cards.sh` 两处失败回滚为纯 `rm -f`（:132、:200）。push 失败时卡其实已被原子段 commit 进 HEAD，调用方的纯文件删除回滚退化为：孤儿 docs(card) 提交 + 工作区 deleted 状态 + 重试生成同号卡的重复历史。触发门槛低至一次网络抖动。
- 根因：给工具新增「先持久化、后报错」语义时，只看了工具自身的行为正确性，没有审计全部调用方对退出码的既定解释与失败清理路径；「改一个文件的语义」在生态里等价于「改所有依赖该语义者的行为」。
- 教训：①凡给共享工具新增/变更退出码语义，同卡内必须枚举全部调用方（grep 调用点）逐一核对失败分支假设，不兼容即视为范围外障碍显式上报，不得默认调用方会自适应；②失败回滚若可能作用于已持久化产物，必须区分「删工作区未跟踪文件」与「撤销已入 git 的产物」（后者需 git 层面回退，纯 unlink/rm 必然留孤儿）；③执行体遇此类跨白名单缺陷：停止实现+如实回写+给出处置选项（扩白名单修调用方 / 修改工具语义须卡面授权 / 接受为已知限制），禁止擅自降级退出码或越白名单顺手修。
