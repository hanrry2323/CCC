# CCC 线路图重构技术方案

> 日期：2026-08-12 · 设计者：Claude Fable 5
> 依据：`CCC-PRIME-DIRECTIVE.md`（最高准则）+ `DOC-PROTOCOL.md`（文档协议）+ qx2/qx03 两份代码级分析
> 状态：方案（待老板确认）

---

## 一、设计目标与约束

### 1.1 目标

将 CCC 三层架构从"概念上有三层、代码上只有两层半"改造为**真正的三层独立数据模型**：

```
线路图（管未来）→ 计划（管当前）→ 看板（管正在进行时）
```

### 1.2 约束

| 约束 | 说明 |
|------|------|
| 零数据库 | 不引入 PostgreSQL/MySQL/SQLite，文件即数据库 |
| 文件系统优先 | 所有持久化落 Markdown 文件，git 可追溯 |
| 向后兼容 | 现有 35 个方案文件不丢失，逐步迁移 |
| 不破坏看板 | 看板六列和 Engine 流转完全不变 |
| 3 个人审节点 | 不可增减（PRIME-DIRECTIVE §4） |

### 1.3 现状 vs 目标

| 维度 | 现状 | 目标 |
|------|------|------|
| 线路图数据模型 | 从 epic 卡动态派生 | 独立 Project + Milestone + Step |
| 草案位置 | 计划页第一栏（五态之一） | 搬到线路图页（草案池） |
| 里程碑 | 无独立概念（借用 epic 卡） | 核心一等公民，独立持久化 |
| 三层关系 | 弱关联（卡名字符串引用） | 级联依赖 + 自动状态回写 |
| 计划状态 | 五态（草案+执行四态） | 三态（已确认→部分执行→已完成） |
| 作废方案 | 保留在计划页 | 作废方案归档，不占计划页位置 |

## 二、数据模型设计

### 2.1 线路图层：Project + Milestone + Step

#### 2.1.1 存储方案选择

**选择：Markdown 文件（与现有方案/卡一致）**

| 候选 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| Markdown 文件 | git 可追溯、人可读可编辑、零依赖 | 需正则解析、并发写入需锁 | ✅ 采用 |
| JSON 文件 | 解析简单、类型安全 | 不可人读、git diff 可读性差 | ❌ 拒绝 |
| SQLite | 查询方便、并发安全 | 引入新依赖、git 不可追溯 | ❌ 拒绝（违反约束） |

**具体方案**：每个项目一个 `roadmap.md` 文件，放在 `docs/projects/<prefix>/roadmap.md`。

#### 2.1.2 文件格式

```markdown
# <项目名> 线路图

> 项目：<prefix> · 更新：2026-08-12

## 草案池

<!-- 每行一个草案，格式：- [意向/问题] <一句话描述> · 来源：<Loop巡查/老板意图/外部反馈> · 日期：YYYY-MM-DD -->

- [意向] 计划页卡片文字被截断 · 来源：老板评审 · 日期：2026-08-12
- [问题] sidecar 挂死根因未根治 · 来源：Loop巡查 · 日期：2026-08-11
- [意向] CCC 开发平台与业务运行层分离 · 来源：老板意图 · 日期：2026-08-09

## 里程碑

### M1 · <里程碑标题> · 目标日期：2026-09-01

> 状态：进行中 · 方案：002-arch-roadmap-upgrade, 003-flow-fix-plan
> 进度：2/3 方案完成

<里程碑描述，1-3 句话>

### M2 · <里程碑标题> · 目标日期：2026-10-01

> 状态：待启动 · 方案：无
> 进度：0/0 方案完成

<里程碑描述>
```

#### 2.1.3 数据模型定义

**Project（线路图文件本身）**

```
Project
├── prefix: str              # 项目前缀（等同 registry）
├── name: str                # 显示名
├── roadmap_path: str        # docs/projects/<prefix>/roadmap.md
├── drafts: list[Draft]      # 草案池
└── milestones: list[Milestone]
```

**Draft（草案条目）**

```
Draft
├── type: "意向" | "问题"       # 来源类型
├── description: str           # 一句话描述
├── source: "老板意图" | "Loop巡查" | "外部反馈"
├── date: str                  # 创建日期
└── status: "待确认" | "已转为方案" | "已关闭"
```

**Milestone（里程碑）**

```
Milestone
├── id: str                   # 唯一标识（从标题派生或序号）
├── title: str                # 人读标题
├── description: str          # 1-3 句话描述
├── target_date: str          # 目标日期（YYYY-MM-DD，可选）
├── status: "待启动" | "进行中" | "已完成"
├── plan_ids: list[str]       # 关联的方案编号（如 ["002", "003"]）
├── progress: {total: int, done: int}  # 实时计算：子方案完成率
└── order: int                # 排序序号
```

**Step（步骤，可选——里程碑内部的子阶段）**

```
Step
├── id: str
├── title: str
├── milestone_id: str         # 所属里程碑
├── card_ids: list[str]       # 关联卡编号（1:1 或 1:N）
├── status: "待开始" | "进行中" | "已完成"  # 从关联卡状态派生
└── order: int
```

**Step 是否必须？** 根据 PRIME-DIRECTIVE 数据模型设计，Step 是里程碑内的子阶段。但当前 35 个方案中，方案拆卡粒度已经充当了 Step 的角色。建议 **Phase 1 不实现 Step**，先用 Milestone 的 plan_ids 直接关联方案即可。Phase 2 再视需要引入。

#### 2.1.4 关系图

```
Project (1) ──< (N) Milestone
  │
  └──< (N) Draft

Milestone (1) ──< (N) Plan (计划层)
Plan (1) ──< (N) Card (看板层)
```

### 2.2 计划层：Plan（改造）

#### 2.2.1 改造内容

| 改动 | 现状 | 目标 |
|------|------|------|
| 状态机 | 五态（草案/已确认/部分执行/已完成/作废） | 三态（已确认/部分执行/已完成） |
| 草案 | 计划页第一栏 | 搬到线路图草案池 |
| 作废 | 计划页最后一栏 | 文件打 `[作废]` 标记，前端不渲染 |
| 与线路图关联 | 无 | 头部新增 `> 里程碑：M1` |
| 字段新增 | 无 | 新增 `milestone_id` 字段 |

#### 2.2.2 新 Plan 文件格式

```markdown
# 方案 · <标题>

> 项目：<prefix> · 编号：<prefix>-plan-<NNN> · 状态：已确认
> 里程碑：M1 · 作者：<作者> · 工具：<工具>
> 创建：2026-08-12 · 更新：2026-08-12
> 关联卡：无
> 关联方案：无

## 目标
...
## 验收标准
- [ ] ...
## 转卡计划
- ...
```

**新增字段**：`里程碑：M1`（可选，未关联里程碑时值为 `无`）

#### 2.2.3 状态机（三态）

```
已确认 ──→ 部分执行 ──→ 已完成
  │                      ↑
  └── 作废（归档） ──────┘
```

- **已确认**：方案已定，等待排期转卡
- **部分执行**：已转卡，有子卡在看板中
- **已完成**：所有子卡已关闭
- **作废**：不再执行，文件保留但标记 `[作废]`，前端不渲染

**与五态的差异**：
- 移除「草案」→ 草案是线路图的概念，不是计划的概念
- 「作废」不再作为计划页的列——它是归档动作，不是活跃状态

#### 2.2.4 状态自动推进

| 触发条件 | 动作 |
|----------|------|
| 转卡成功 | `已确认` → `部分执行`（与现在一致） |
| 所有关联卡已关闭 | `部分执行` → `已完成`（**新增自动化**） |

**自动推进到「已完成」的实现**：在 `plans.py:list_plans` 或一个独立的巡检函数中，检查方案的所有关联卡是否都已关闭。若是，自动将方案状态改写为「已完成」。这个逻辑可以放在 `validate-plans.sh` 定时巡检中，或作为 Engine 的回写步骤。

### 2.3 看板层：Card（不变）

看板六列和 Engine 流转逻辑**完全不变**。唯一的改动是：
- 卡文件头部新增可选的 `> 方案：<prefix>-plan-<NNN>` 字段，用于反向溯源（当前已有 `关联` 字段，可复用）

### 2.4 统一数据关系

```
Project (roadmap.md)
  │
  ├── Draft[]
  │     └── 老板确认 → 转为方案
  │
  └── Milestone[]
        │
        └── plan_ids[]
              │
              └── Plan (plans/<NNN>-<slug>.md)
                    │
                    ├── status: 已确认/部分执行/已完成
                    ├── milestone_id: "M1"
                    │
                    └── cards[]
                          │
                          └── Card (dispatch/<prefix>/<prefix><NNN>-<slug>.md)
                                │
                                └── state: 待分派/执行中/已回写/已关闭/打回
```

## 三、状态回写机制

### 3.1 回写链

```
看板卡状态变化
  │
  └──→ 方案进度计算（子卡关闭率）
        │
        └──→ 方案状态自动推进（全关→已完成）
              │
              └──→ 里程碑进度计算（子方案完成率）
                    │
                    └──→ 线路图总览更新
```

### 3.2 触发时机

| 回写 | 触发时机 | 实现方式 |
|------|---------|---------|
| 方案进度 | 每次 `/plans/list` 或 `/plans/card-states` 查询时实时计算 | 读关联卡文件，统计关闭数 |
| 方案自动完成 | Engine 关闭卡后，或 `validate-plans.sh` 定时巡检 | 检测全关→自动推进状态 |
| 里程碑进度 | 每次 `/roadmap` 查询时实时计算 | 读关联方案文件，统计完成数 |
| 线路图总览 | 随里程碑进度更新 | 聚合所有项目里程碑 |

### 3.3 缓存策略

与现有 `_BOARD_CACHE` 一致：20 秒 TTL，按文件 mtime 变化自动失效。

## 四、API 端点设计

### 4.1 新增端点

| 端点 | 方法 | 参数 | 返回值 | 说明 |
|------|------|------|--------|------|
| `/roadmap` | GET | 无 | `{projects: [{prefix, name, milestones, drafts}]}` | 线路图总览（替代 `/board/roadmap`） |
| `/roadmap/<project>` | GET | 路径参数 | `{prefix, name, milestones, drafts}` | 单项目线路图 |
| `/roadmap/<project>/milestone` | POST | `{title, description, target_date?}` | `{ok, id}` | 创建里程碑 |
| `/roadmap/<project>/milestone/<id>` | PUT | `{title?, description?, target_date?, status?, plan_ids?}` | `{ok}` | 更新里程碑 |
| `/roadmap/<project>/milestone/<id>` | DELETE | 路径参数 | `{ok}` | 删除里程碑（仅当无关联方案） |
| `/roadmap/<project>/draft` | POST | `{type, description, source}` | `{ok}` | 新增草案 |
| `/roadmap/<project>/draft/convert` | POST | `{draft_index, author, tool}` | `{ok, plan_id, plan_path}` | 草案→方案（人审节点①） |

### 4.2 修改端点

| 端点 | 改动 |
|------|------|
| `GET /plans/list` | 返回数据结构不变，但 `status` 只返回三态（已确认/部分执行/已完成）；新增 `milestone_id` 字段 |
| `POST /plans/create` | 新增可选参数 `milestone_id`；不在头部写入「草案」（初始状态为「已确认」） |
| `POST /plans/update` | 支持更新 `milestone_id` |
| `GET /plans/card-states` | 不变 |
| `POST /plans/convert` | 不变 |
| `GET /plans/detail` | 返回新增 `milestone_id` 字段 |

### 4.3 废弃端点

| 端点 | 理由 |
|------|------|
| `GET /board/roadmap` | 被 `/roadmap` 替代 |
| `GET /board/roadmap/<project>` | 被 `/roadmap/<project>` 替代 |

### 4.4 前端路由

| 路由 | 页面 | 数据源 |
|------|------|--------|
| `#/roadmap` | 线路图页（重构） | `GET /roadmap` + `GET /roadmap/<project>` |
| `#/plans` | 计划页（改造） | `GET /plans/list`（三列） + `GET /plans/card-states` |
| `#/board` | 看板页（不变） | 现有端点不变 |

## 五、数据流设计

### 5.1 创建流程

```
老板/Agent 在线路图页输入意图
  │
  ├──→ 意图进入草案池（草案条目）
  │
  └──→ 老板确认草案（节点①）
        │
        ├──→ 系统调用 POST /roadmap/<project>/draft/convert
        │     ├── 创建方案文件（状态=已确认，关联里程碑）
        │     └── 草案状态标记为「已转为方案」
        │
        └──→ 方案出现在计划页「已确认」列
              │
              └──→ 老板确认转卡（节点②）
                    │
                    ├──→ POST /plans/convert
                    │     ├── 生成任务卡
                    │     └── 方案状态 → 部分执行
                    │
                    └──→ 卡进入看板，Engine 自动流转
                          │
                          └──→ 卡全关 → 方案自动 → 已完成
                                │
                                └──→ 里程碑进度自动更新
```

### 5.2 状态回写数据流

```
Engine 关闭卡
  │
  ├──→ 卡状态变为「已关闭」
  │
  ├──→ 方案进度实时计算（/plans/card-states）
  │     └── 全关 → 巡检自动推进方案为「已完成」
  │
  ├──→ 里程碑进度实时计算（/roadmap/<project>）
  │     └── 子方案全部完成 → 里程碑状态 → 「已完成」
  │
  └──→ 线路图总览（/roadmap）
        └── 总进度条实时更新
```

### 5.3 Loop 螺旋巡查

```
Loop 定时巡检
  │
  ├──→ 发现：方案已完成但关联卡未关闭 → 告警
  ├──→ 发现：里程碑过期 → 告警
  ├──→ 发现：草案超过 N 天未处理 → 提示
  ├──→ 发现：挂账无方案 → 提示
  │
  └──→ 问题自动回线路图草案池
```

### 6.1 现有数据盘点

| 数据 | 数量 | 位置 | 迁移动作 |

| 方案文件 | 35 个 | `docs/projects/*/plans/` | 改状态机 + 加里程碑字段 |

### 6.2 迁移步骤

#### Phase 1：数据模型落地（无破坏性）

1. 新增 `roadmap.py` 模块（`server/board/roadmap.py`）
   - 读/写 `docs/projects/<prefix>/roadmap.md`
   - 草案条目 CRUD
   - 里程碑 CRUD
   - 进度实时计算

2. 新增 `/roadmap` 和 `/roadmap/<project>` API 端点
   - 暂时与 `/board/roadmap` 并存（逐步切换）

3. 为每个有方案的项目创建初始 `roadmap.md`
   - 从现有方案中提取里程碑分组（手动或半自动聚类）
   - 4 个草案方案转为草案条目

4. 改造 `plans.py`
   - 状态机从五态改为三态
   - 新增 `milestone_id` 字段读写
   - 自动推进「已完成」逻辑

#### Phase 2：前端切换

5. 重构 `#/roadmap` 页面
   - 草案池视图（替代计划页第一栏）
   - 里程碑时间线（保留现有图形化渲染）
   - 草案→方案转换按钮（节点①）

6. 改造 `#/plans` 页面
   - 三列布局（已确认/部分执行/已完成）
   - 每列显示关联里程碑
   - 移除「草案」和「作废」列

7. 切换 `/board/roadmap` → `/roadmap`
   - 前端改数据源
   - 废弃旧端点

#### Phase 3：清理与加固

8. 清理死代码
   - `queries.py` 中 `roadmap_aggregate` / `roadmap_project_detail`
   - `roadmap_parser.py` 中从 epic 派生的旧逻辑

9. 增加并发安全
   - `_next_num` 加锁
   - `create_plan` 原子写入
   - `update_plan` 读写锁

10. 更新文档
    - `DOC-PROTOCOL.md` 状态机改为三态
    - `CCC-PRIME-DIRECTIVE.md` 同步更新
    - `INDEX.md` 更新三层架构描述

## 七、实施优先级

### 优先级排序（按价值/风险比）

| 优先级 | 任务 | 价值 | 风险 | 说明 |
|--------|------|------|------|------|

| P1 | 里程碑与方案关联 | 高 | 中 | 需改方案文件头部 |
| P2 | 重构 `#/roadmap` 前端 | 高 | 中 | 保留现有图形化组件 |

## 八、风险与对策

| 风险 | 概率 | 影响 | 对策 |
|------|------|------|------|
