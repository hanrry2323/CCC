### 2.3 设计亮点（⭐ 可复用做法）

1. **红线制度**：33 条不可触犯红线（数字 1–20 + X1–X8 + R-04/07/08/09/12/14/15），触犯即记 Critical 违规 + Lesson 沉淀。[red-lines.md](file:///Users/apple/program/CCC/references/red-lines.md#L1-L80)
2. **Lesson → 红线 → 代码的闭环学习飞轮**：失败经验文档化 → 固化为红线 → 写进 Engine/门禁代码。见 [lessons.md](file:///Users/apple/program/CCC/docs/lessons.md)
3. **无穷角色机制**：Skill + Prompt = 本次角色（非 7 个固定角色）；仓库里 `skills/ccc-*` 是流水线默认能力包，不是用户点选的角色超市
4. **控制面四态机**：`disabled / ui / enabled / invent`（invent 已 `INVENT_HARD_DISABLED=True`）+ 红线 12「禁止 agent 自主启用 CCC」。[CONTROL.md](file:///Users/apple/program/CCC/docs/CONTROL.md)
5. **ADR 架构决策记录**：`docs/adr/` 下 5 份（协议层 / Runtime 适配 / Scheduler 适配 / 多平台编排 / 日审闭环）
6. **KPI 压力测试闭环**：2026-07-22 ~ 07-23 连续跑 KPI R1–R5 5 轮：`eval → fix → opt-plan`，并出 stress-efficiency / capacity-probe / gate-rule-fitness / ops-confidence 专题 Brief（见 `docs/briefs/` 30+ 份）

### 2.4 架构级问题（⚠️ 07-24 五维度审计实锤）

来自 [2026-07-24-audit.md](file:///Users/apple/program/CCC/docs/stability/2026-07-24-audit.md#L1-L150) 5 份并行只读审查的综合结论 —— **不是将来风险，是已经在生产中爆发的工程债务**，且都是跨模块**同型缺陷**（统一假设错误）：

| 类别 | 统一假设错误 | 业务体感 | 严重度 |
|------|--------------|----------|--------|
| **① 写入非原子** | 「用了 `os.replace` 就是原子写」（缺 fsync / 目录 fsync / journal / 事务） | 用户视角的 "任务消失"、"卡死"、"重复 launch" | 🟥 最严重 |
| **② 可观测性在骗你** | 「写了 events.jsonl 就有可观测性」（异常被吞 / 缺关键事件 / append 无 fsync） | 看板状态、upstream 状态全是有偏样本 → 看不到问题 = 问题不存在 | 🟧 第二严重（掩盖①） |
| **③ 进程生命周期失控** | 「Popen 包了 try/finally 就安全」（只清 pid_file，子进程树不递归 / stdout=PIPE 64KB 死锁 / watchdog 硬退） | stress/medium fanout 已知爆雷（Lesson 44）、孤儿进程泄漏 | 🟧 第三严重 |
| **④ 门禁形同虚设** | 「reviewer 写了 verdict 就完成门禁」（reviewer 可跳过 tester / verdict 空文件兼容 / 重试爆炸 → 单卡最多 ~54 次重试） | 以为过了 tester 实际没生效；LLM fail 当 transient 一直重试成本不可控 | 🟨 第四严重 |
| **⑤ 红线 12 无实防** | 「agent 自己不主动 set_mode enabled 就够了」（source 白名单空 / 控制面写入无共享锁 / 默认口令 ccc:ccc + 0.0.0.0） | 同网段任何脚本能停 Engine、改写 control.json、读取失败账本 | 🟨 第五严重（安全相关） |

修复路线图：[2026-07-24-fix-plan.md](file:///Users/apple/program/CCC/docs/stability/2026-07-24-fix-plan.md#L1-L99) 已分 3 批 ROI 排序（第 1 批 < 1 day 堵漏，第 2 批 1–2 week 原子化，第 3 批 2 week+ 测试盲区）

### 4.1 CI 流水线（GitHub Actions，[ci.yml](file:///Users/apple/program/CCC/.github/workflows/ci.yml#L1-L133)）

| Job | 作用 |
|-----|------|
| `version-sync` | check-version-sync.py 断言 VERSION 与 Tauri/Cargo/npm/package.json 一致 |
| `pytest` | macOS runner；先跑 py_compile 所有 scripts/*.py 和 bash -n 所有 *.sh；再 pytest tests/scripts |
| `ruff` | `ruff check scripts/ tests/ examples/`，ruff-action v1 固定版本 0.8.6 |

| `precommit` | 若存在 .pre-commit-config.yaml 就跑 |
| `e2e` | Pipeline smoke + Green pipeline e2e + F1 backlog failover（3 份 bash e2e） |
| `selfcheck` | bash scripts/ccc-self-check.sh（语法 + 安全扫描） |
| `scripts-tests` | pytest scripts/tests/（Hub 路由 / voice / transfer_gate 内嵌测试） |

**优点**：macOS runner 跑 launchd 相关 shell 脚本不水土不服；先语法烟测再跑测试；8 Job 覆盖 4 语言。

### 4.2 测试缺口（审计 F-ARCH-02）

- 数量 102 vs Python 186 → 覆盖率仍偏防御性
- **结构盲区**：并发竞态、auth fail-closed、reviewer 门禁绕过——这些结构性问题很难靠单元测，需要集成测试框架

- 好迹象：KPI R1–R5 每轮 fix 后跟进补 `test_kpi_r*.py`，修复即补单测习惯在建立

### 7.4 对标结论：CCC 的独特价值在哪？

#### ✅ CCC 在同类里具备 **3 个真差异化**（社区竞品没同时做）：

1. **对话面 / 编排面双机分离的硬边界**
   - 竞品通病：单机器 monolith。你聊天的那台机器同时要跑 OpenCode 扇出、测试、评审，笔记本 CPU 被打满、风扇狂转，且大任务要开着电脑等。
   - CCC 解法：M1 做对话（低负载），Mac2017 做写码+验收（高负载，可远程常驻）。中间只交 epic 和状态流，用户不用盯后台跑。
   - 这与 SaaS 类 Devin / E2B 思路类似，但 CCC 是**全本地 / 自托管 / 代码不出内网**。

2. **无穷角色 + 看板闭环 + 红线制度：把 AI Coding 当工程流程管，而不是当"聊天工具"**
   - 竞品通病：「一个 LLM Agent 一把梭」—— 拆需求、写码、测试、评审都在同一会话，长上下文混乱，且无结构化门禁。
   - CCC 解法：把软件工程的**角色分工 / 阶段流转 / 验收门禁 / 失败复盘**做成可执行机制（product→dev→reviewer→tester→ops→audit→kb，7 角色 + 看板 + 33 红线 + Lesson 沉淀）。
   - 这点更接近「公司级研发流程自动化」，而不是「个人开发者聊天写代码」。

3. **可插拔执行面（非锁定单一 IDE/执行器）**
   - 竞品通病：Cline 绑 IDE，Aider 绑 CLI Shell，Cursor 绑 VS Code fork。
   - CCC 解法：执行器是插件，默认 OpenCode，已预留 Python / Ollama / CLI Executor / Claude CLI 接口。不跟任何一款工具锁死。

#### ⚠️ CCC 在同类里的 **2 个明显短板**（社区竞品已跑在前面）：

1. **无公开 Benchmark 结果 = 无硬实力证**
   - 社区所有主流 Agent 都在 Terminal-Bench 2.1 / SWE-bench Verified / ML-Bench 上有公开分，CCC 没跑。即使你主张"Benchmark 测的是模型不是架构"，你也**至少得有一次基线证明**——否则对外讲故事缺弹药。
   - 建议：花 2–3 天用 Sonnet 4.6 跑 Terminal-Bench 2.1 全量，做一次基线；后续再测架构层面的多任务扇出吞吐（CCC 真正差异化的部分），而不是 SWE-bench 单任务模型分。

2. **工程债在 07-24 审计中实锤 5 大类 15 子项——稳定度可能不如社区头部**
   - Aider / OpenCode / Cline 作为百万用户级产品，进程生命周期、文件原子写、并发安全经过海量用户踩踏，边角比 CCC 稳。
   - 反过来看：这恰恰是 CCC **可快速追赶**的部分——因为有明确修复计划（07-24-fix-plan），且都是确定性的工程问题，不是产品定位问题。

### 7.5 对标启示：CCC 的护城河打法建议

根据 2026-06 横评作者的核心结论「**按任务类型路由 > 选最强模型**」（同任务 Sonnet 4.6 和 Opus 4.6 质量 100% 相同，价格差 3.5 倍；Gemini Flash 38 任务 $0.003 跑完 52 秒，92% 通过），CCC 有天然优势承接：

- CCC 已经有 `_config.py` 里 `model_tiers` + fallback_providers（虽然当前 07-24 审计 M7/L1 说 "fallback_providers 无调用方读" —— 底子已经有）
- CCC 的 phase 级角色分工天然适合做 **phase 级模型路由**：
  - product 对齐 → Sonnet 4.6（$0.20）
  - kb 归档 / 简单 diff → Gemini 2.5 Flash（$0.003）
  - reviewer 审查 medium/large + 复杂重构 → Opus 4.8（$0.69+）
  - 离线 / 敏感代码 → 本地 GPT-oss-20b / Gemma 3 12B（$0）
- 这套路由写进 Engine phase 调度里，会比社区竞品目前的「手工 alias」方式优雅得多，且能接 CCC 已有的 stress-kpi-gate：**按 KPI 动态调模型档位**，成本可降 71%（参考横评作者实测 247→48 美元）。
