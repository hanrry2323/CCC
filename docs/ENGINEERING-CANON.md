## 〇、一句话总纲

**CCC 是一台 Loop Engineer**：卡是承诺（期望），Agent 是执行（写码），机审是裁判（本次质量），审核是阶段验收（整体交付），门禁是底线（机械强制）。**用户提需求，不提 bug——验收环节把问题做完，不留给用户找 bug。**

## 〇·五、意图开发原则（CCC 的灵魂 · 硬）

> 2026-08-11 老板定调：**主观只存在于人的意图层，Agent 没有主观。**

1. **Agent 不判主观**：美观/体验/设计品味等主观标准，不归任何 Agent 判定（机审/审核/Loop 都不判）。Agent 只处理可判定的硬标准。
2. **主观意图通过对话表达**：主观需求由老板 ↔ IDE 工具对话表达，Agent 理解意图后开发实现。这就是 CCC 的核心——**意图开发**。
3. **CCC 底座 = 意图开发的制度化**：普通 IDE 对话式开发（聊→开发→验收）已有 CCC 底座支撑——记录留痕、集群开发、流程架构。**意图在对话层，执行在流程层**。
4. **验收环节做硬验收**：前端/后端功能验收是硬标准（页面能打开、按钮能点、接口走通），可机器判定；主观合意由人在对话中判断。
5. **不要试图让 Agent 理解主观**：主观是不可判定的，硬塞给 Agent = 死循环 + 不可复现打回。

## 一、宪法：核心工作原则（十条）

> 定稿版与三路验证数据：`__archive__/decisions/CCC核心工作原则十条-2026-08-11.md`

### 根原则（一至五）

**1. 先止血，再挖根因，最后改流程。**
现场止损 → 定位根因 → 改流程本体。补丁允许存在但**禁止转正**：每笔止血打标（卡上标注「止血」，进债务清单）；定期全量梳理，按根因归并——能并进流程固有步骤的并进，不能的重构成架构改进。循环一轮，架构上抬一档。
> 2026-08-11 印证：clw019 sidecar 残留挂 7 小时，只留了 lessons 文档、**没有代码修复**——这是「止血未转正」的反例，已列入本规范根因修复清单（见 §三-1）。

**2. 落点要对，步子要小。**
正确性是落点问题，不是体量问题。宁可多拆几步，不可落错一层。「改得大」不是美德。
> 2026-08-11 印证：跨节点路由的正确落点是「Worker 模型 + 认领协议」，不是「手动 GUI 分类 + manual 派发」两层补丁（见 §三-3）。

**3. 每个改动带自证。**
不靠「试了能跑」。单测管逻辑、集成测管联调、演练管流程。机审负责核，门禁负责卡。
> 2026-08-11 印证：观测指标「ccc-kb 调用 0 次」是假数据——observer 正则匹配不到 ANSI 色码日志，实际单卡 98 次。自证必须校验数据真实性，不只是"有输出"。

**4. 废弃机制带退役条件与观察窗。**
新旧并行必须立「退役条件 + 观察窗 + 单一真源」。没有这三样的并行，一律按僵尸叠加清退。
> 2026-08-11 印证：sidecar 状态「只写不清」= 双源漂移（磁盘 vs sidecar）无收口，见 §三-2。

**5. 流程有缺陷改流程，不攒特例。**
每发现一个「绕过流程」的操作，追问：是流程错了，还是人在偷懒？前者改流程，后者改人。豁免必须打标 + 明确条件 + 复盘。

### CCC 红线（六至八）

**6. 平台不自我开发。**（硬）
引擎/门禁/出卡类「流程本身」改动禁止走卡委派，M1 直接开发 + 异席机审。防「补丁卡→平台更不稳→更多补丁卡」自激增长。

**7. 异席机审。**（硬）
写的人不审自己。机审主体与被审对象不同源，执行与验收至少跨机或跨席。异席机械强制须在 onboarding 固化。

**8. 卡是承诺，不是过程。**
卡上写验收条件，不写步骤。回写带维护区四问自证闭环（方案同步/教训/档案/线路图），缺一拒收，填假打回。

### 代码与架构（九至十）

**9. 代码是负债，不是资产。**
能删不加，能简不绕。写前问三句：已有机制能不能覆盖？这是功能还是补丁？删了会不会有人哭？优雅 = 换个人三个月后能看懂且敢改。

**10. 红线预警，动前自检。**
改代码/流程前先过红线清单。红线一票否决，碰了直接拒。自检要真查，禁止自我解释放行。

## 二、验收体系（机审 + 审核 + Loop 三层）

> 三层分工：**机审**（单卡立即审·窄而硬）→ **审核**（阶段整体验收）→ **Loop**（后台持续审·只审不投）。三层都只判**可判定的硬标准**；**主观标准不归任何 Agent 判定**（Agent 无主观），主观只在人的意图层通过老板↔IDE 对话表达（意图开发核心）。详见 [`product/machine-audit-sop.md`](product/machine-audit-sop.md) + [`product/loop-human-gate-sop.md`](product/loop-human-gate-sop.md)。

### 2.1 机审（本次开发质量）——现有，强化

**职责**：审查本次开发的代码质量、是否破红线、规范符合度。机审是「裁判」，判的是这次改动好不好。

**强化点（2026-08-11 探查）**：
- 机审对「声明不实」已能打回（clw019 实证：报告不在 main → 打回「维护区声明不实」）✅
- **缺口**：机审只审「代码 + 维护区声明」，未覆盖「前端/后端功能验收」（见 2.2/2.3）
- **缺口**：机审打回 → sidecar 残留待分派无自动清理（见 §三-2，本规范要求根治）

### 2.2 前端验收规范（新增 · 页面级功能验收）

> 核心：**前端不是"代码能跑就过"，是"页面表达/元素/显示符合设计、功能全部实现"**。用户提需求，不找 bug。

**验收维度**：
1. **页面表达**：布局、层级、信息架构符合需求/设计稿
2. **页面元素**：每个按钮/输入/列表/弹窗真实存在且可交互；**每个可点击元素实际点击验证**（不只是代码里有 onClick）
3. **页面显示**：样式生效（CSS 变量/主题正确）、响应式、无布局错乱
4. **功能闭环**：需求列的功能**逐条在浏览器中走通**（打开页面 → 操作 → 观察结果），不是"代码实现了所以对"
5. **边界状态**：空态/加载态/错误态/成功态都有正确表现

**验收手段**：浏览器级验证（Playwright/浏览器自动化），不只读代码。步骤：打开页面 → 逐元素点击 → 逐功能操作 → 核对显示与状态 → 记录证据。

**落在哪**：机审环节的前端项 = 跑浏览器验收；审核环节 = 整站走查。前端开发卡的红线/范围/验收标准模板要含「浏览器验证」条目（见 §五-3）。

### 2.3 后端验收规范（新增）

**验收维度**：
1. **接口行为**：每个 API 真实调用验证（请求/响应/状态码），不只「测试通过」
2. **数据闭环**：写→读→改→删全链路真实走通
3. **错误处理**：异常输入/超时/依赖故障有正确响应
4. **边界**：鉴权/权限/参数校验/幂等
5. **集成**：跨服务/跨模块真实联调

**手段**：接口级验证（curl/脚本/集成测试）+ 真实数据演练，不只单元测试。

### 2.4 审核（阶段整体验收 · 新增环节）

**定位**：机审审「本次开发」，**审核审「一个阶段/一个版本的整体交付」**——机审完了之后的独立环节。

**触发**：方案内关联卡全部关闭 / 一个开发阶段结束 / 版本发布前。

**职责**：
1. **整体一致性**：所有卡合起来是否构成可用交付（不是单卡各自对）
2. **验收标准对账**：方案验收标准逐条核对（对应前端/后端验收规范）
3. **交付物**：按 `onboarding.md §7 Delivery Gate` 核对交付物（打包/安装/验收报告/版本）
4. **回归**：跨卡改动是否有互相破坏
5. **质量总评**：是否达到「可交付/可用」标准

**与机审关系**：
```
单卡开发 → 机审（本次质量） → 合入
         └→ 阶段结束 → 审核（整体交付） → 验收报告 → 交付/发布
```

**责任人**：审核由异席（验收席/老板）执行，不能是开发同源。审核产出：阶段验收报告（用 `projects/_template/delivery-template.md`）。

## 三、架构根因修复清单（2026-08-11 探查 · 本规范要求根治）

> 原则：**架构升级，不做补丁**。每项是根因修复，不是加应急逻辑。均按红线 6「平台不自我开发」→ M1 直接开发。

### 1. sidecar 状态生命周期契约（clw019 根因）

- **现状**：sidecar（`~/.ccc/logs/exec/state/cards.jsonl`）只写不清；Engine 全程 0 次 clear；机审打回写「待分派」但磁盘卡不动 → manual/未登记卡挂死；看板被 sidecar 覆盖显示失真。
- **根因**：「打回→重试」语义 + 「sidecar 覆盖磁盘」规则 + 「无人清 sidecar」三个决策叠加，无收口保证。
- **修复**（架构级）：
  1. 定义 sidecar 生命周期契约：sidecar = 在途执行态；终态（已回写可合入/打回/已关闭）由磁盘卡 + 分支信封唯一权威。
  2. `_run_auto_worker` 每个出口显式收口（成功/打回/重试/跳过四分支明确写 or clear）。（2026-08-29 更新：legacy 机审 `_run_audit_worker` 已按 ccc-plan-053 C0 拆除，验收席唯一座席=phase2 CC，本条只约束执行 worker。）
  3. 收敛器入 `run_once` 循环（把 `sync-runtime-state.py` 逻辑搬进 Engine，去掉人工依赖）。
  4. `_fail_retry_or_reject` 拆「不可自愈（manual/未登记/冷却）→ 立即 clear」路径。
- **判定**：clw019 事故无代码修复 = 止血未转正，本项转正。

### 2. Engine 建造型假设 vs 集群 Worker（跨节点路由根因）

- **现状**：Engine 唯一执行通道是 `subprocess.Popen`（本机子进程）；W9 靠「手动 GUI」+「manual 派发」两层补丁绕开，**不是真路由**。实测 `W9+engine` 会回退 2017 本地拉起。
- **根因**：`ExecutorEntry.worker_id` 是追溯标签不是路由地址；决策路径 `rows_for_binding` 不认 worker_id，执行路径 `cli_entry_for_binding` 认——两条路语义相反（RC4）。
- **修复**（架构级）：
  1. Worker 模型升级：`ExecutorEntry` 加 `host/transport/worker_status`，Worker 是带地址与状态的一级对象。
  2. 决策路径与执行路径寻址对齐：`decide_work` 改认 worker_id，加 `REMOTE` 决策态。
  3. 认领协议 v1（复用 git 信道）：Engine 投递 → Worker 认领（lock marker）→ 执行 → 回写 → Engine 按「认领/在途」收单，不再靠本地 PID。
  4. 机审对 remote 卡显式适配（无本地 worktree 路径）。
- **判定**：「手动 GUI + manual」= 双层补丁，废弃；改 Worker 模型 + 认领协议。

### 3. role-skills 注入一致性

- **现状**：skill 本体三处不同步（M1/2017/252 手工 scp）；注入在出卡时烘死（改 yaml 存量卡不更新）；无「节点 × skill × 版本」校验。
- **修复**：skill 收进 CCC 仓（`server/config/claude-skills/` 已是雏形）→ 一键下发/校验脚本；role-skills 注入点从出卡改派发时动态 + 校验目标节点 skill 存在。

### 4. 观测指标数据真实性

- **现状**：指标「ccc-kb 调用 0 次」是假数据（ANSI 色码正则不匹配）。
- **修复**：observer 去 ANSI 色码再匹配，校验数据真实性。

## 四、Agent 心智升级方向

> CCC 流程里每个 Agent 是通用智能体，叠加 MCP + Skill 后成为专用智能体。心智 = 通用心智（qx-map 集群全貌）+ 专用技能（skills+MCP 按角色加载）+ 任务角色（卡头「角色」字段）。

**心智分层**：
1. **通用心智**（qx-map）：集群全貌 / Worker 登记 / 路径权威 / 红线。所有节点要有（2017 已接，252 已接，标准化走 `docs/bootstrap.md`）。
2. **专用技能**（skills+MCP）：按「角色」加载（`server/config/role-skills.yaml`）。skill 版本一致性见 §三-3。
3. **任务角色**（卡头「角色」字段）：任务卡定义本次当什么专家，完成后回通用状态。

**节点心智对齐**：新节点接入 = clone qx-map + 配模型出口 + 节点身份注入 + 验证（bootstrap.md 全流程）。

**Agent 自进化机制**（待建）：
- 教训回流：Doc-Gate 教训沉淀 → 派发模板注入（clw 教训已在做）
- 观测驱动：Skill/MCP 生效观测 → 数据反哺角色映射与 skill 配置
