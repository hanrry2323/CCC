## 〇、定位声明（2026-08-14 强化 · 先读这一条）

> **一句话：CCC 是「意图开发平台」，不是「代码开发工具」。我们做的是编排，不做工具。**

### 我们是什么

**意图开发平台。** 意图开发 = 把模糊想法固化为结构化、可执行、可验收的开发指令，并对指令全生命周期负责。四要素：

1. **孕育**（草案池 / 线路图里程碑）
2. **澄清**（对话收敛，只问一句，不做问卷）
3. **固化**（功能卡 + 验收点 → 任务卡）
4. **闭环**（看板五态 + 机审/合入 + Loop 反哺）

### 我们不是什么

- **不做 IDE / 编辑器**，不造 agent 执行引擎 / harness —— 那是执行层的活。
- **不跟执行层竞争「谁写代码快」。** 我们的战场是「意图从哪来、怎么确认、干完算不算数」——这类能力（文档 / 项目管理 / 进程管理 / 项目周期管理）Harness 天生没有。

### 怎么协同开发工具（执行层 = 可替换槽位）

**执行层工具 = 可替换、可叠加的执行体槽位。** 三层金字塔喂给执行层的不是人话，是**卡**（结构化、带验收点的开发指令）。谁执行不重要——DeepSeek Harness（headless）、Claude Code、OpenCode 都按 `executors.json` 注册表接入，退出码收单，走五态状态机。执行层永远不决定意图。

### 一切皆插件（2026-08-14 吸收 DeepSeek Harness 理念）

**DSH「一切皆插件」对意图层同样成立：Skill、Worker、节点、门禁、回写——本质上都是插件**：可独立加载/卸载、可替换、可组合。意图层持续向「组件可替换、无特权核心」演进，与 DSH 的 Cordis 插件树同构。不照搬框架，吸收「可替换性」作为流程设计的默认取向。

### 下一步重点接入执行体：DeepSeek Harness（DSH）

DSH 定位为下一步重点接入的 IDE 工具 / 执行层执行体：① 模型同源（DeepSeek 系，与 OpenCode + deepseek-v4-flash 同池）；② headless 模式天然契合「薄驱动 Engine + 注册表拉起 + 退出码收单」契约；③ Trajectory 轨迹可作验收证据自动原料，补观测短板。

### 2.1 里程碑模型（2026-08-14 定稿 · 三层架构的骨架）

> **一句话：草案池 = 无限想法（不占开发资源）；里程碑 = 正式开发唯一入口（列入里程碑 = 老板拍板 + 排期 + 进入开发）。已完成里程碑封板，新工作一律新里程碑。**

| 概念 | 语义 | 生命周期 |
|------|------|---------|
| **草案池** | 未排期想法/意向/问题，**不占开发资源**，可以有无数条 | 丢想法 → 老板确认方向（转里程碑）或 清理移除 |
| **里程碑** | 正式开发容器，**进入里程碑 = 正式进入开发流程** | 待启动 → 进行中 → 已完成（封板） |
| **子项目** | 里程碑的分解单元（2026-08-16 决策，覆盖 027「无独立中间层」定义）。每个子项目有独立开发方案+文档；未激活只停留 roadmap，不占开发资源 | 未启动 → 计划中（激活转方案）→ 已完成 |
| **方案** | **一个子项目**的开发方案（1:1），**非整个里程碑**——杜绝「里程碑级一次全投」 | 已确认 → 部分执行 → 已完成 / 作废 / 已覆盖 |
| **功能卡/任务卡** | 方案内拆解的执行实体，声明【颗粒度 / 依赖 / 架构位置】开发卡三要素 | 待分派 → … → 已关闭 |

**演化规则（硬）**：
1. **已完成里程碑封板**：🟢 里程碑不再追加卡/功能（保持验收口径历史一致）；追加一律新里程碑。
2. **新工作先入草案池**：任何新功能/新组件/技术路线变更，先落草案池（意向+来源+日期），老板确认方向后才转方案。
3. **里程碑单向追加**：时间线只往后加（新里程碑），历史里程碑不改。
4. **技术路线变更 = 里程碑级**：新建架构升级里程碑 + 迁移方案（含兼容/不回归/双轨验收）；被完全替换的旧方案标「已覆盖」，历史卡/里程碑保持已关闭/已完成（可审计）。
5. **维护是里程碑**：已发布版本后的 bug 修复/补丁 = 维护里程碑（如 v0.9.1），不并入已完成里程碑。
6. **草案池可清理**：被否决/过时/合并的草案要能关闭/移除，避免积压成垃圾场。
7. **里程碑先拆子项目，逐个逐步投入（2026-08-16 硬）**：大里程碑必须先结构化解耦为子项目（roadmap.md `- 子项目：`），老板在节点① 逐个激活子项目 → 1:1 生成方案 → 按依赖顺序逐步转卡。**禁止「一个方案装整个里程碑、一次全转」**；已封板里程碑不回溯。

**里程碑状态色（看板/线路图渲染）**：🟢 已完成（100%）· 🟡 进行中 · 🟠 部分完成 · 🔴 阻滞/受阻 · ⚪ 未启动。

## 三、三层数据关系

```
线路图.里程碑
  ├── 1:N → 子项目（2026-08-16 结构化分解单元）
  │         ├── 1:1 → 计划.方案（激活后生成；方案 = 一个子项目）
  │         │         ├── 1:N → 看板.任务卡
  │         │         └── 状态回写 → 计划.方案.进度
  │         └── 状态回写 → 子项目.状态
  └── 状态回写 → 线路图.里程碑.进度
```

单向依赖 + 状态回写：
- 里程碑进度 = 子项目完成率（有子项目时）；旧格式里程碑退回子方案完成率
- 子项目进度 = 关联方案完成率
- 方案进度 = 子卡关闭率
- 卡状态 = Engine 全自动流转

## 四、人审节点（3 个，不可增减）

| 节点 | 位置 | 动作 | 为什么不能自动 |
|------|------|------|---------------|
| ① | 线路图 → 计划 | 老板确认里程碑/方案 | 意图判断——只有老板知道"现在做什么" |
| ② | 计划 → 看板 | 老板确认转卡 | 最后防线——确认拆卡方向正确 |
| ③ | 看板 → 部署 | 合入批准 | 代码 diff 终审——不可绕过 |

**只有这 3 个。** 其他一切流转由 Engine 自动完成。

### 4.0 人审调整动作（确认 / 修改 / 取消 · 2026-08-14 统一化）

人审时老板的调整不产生新流程，只在这 3 个节点上行使**否决权/修正权**。所有调整归到 3 种语义：

| 语义 | 定义 | 在各阶段的落地 |
|------|------|----------------|
| **确认** | 放行 | 草案确认（节点①）/ 转卡（节点②）/ 合入批准（节点③） |
| **修改** | 改内容再走 | 改草案（节点①）/ 改方案内容或功能卡清单（节点②）/ 打回+批注（节点③） |
| **取消** | 不再执行 | 草案移除（节点①）/ 方案作废（节点②）/ 卡作废（节点③） |

**判定规则（怎么确定）**：
1. **时间点决定语义**：未转卡取消 = 方案作废；已转卡取消单卡 = 卡作废；已执行要改 = 打回。
2. **向下级联、向上只读**：卡变动只回写方案进度；方案作废级联其未关闭关联卡；里程碑进度由方案完成率算，作废方案剔除。
3. **终态不可逆**：已关闭 / 已完成 / 作废 / 已覆盖 都是终态，改不动。

### 4.1 功能完成定义（验收底线 · 硬）

任何前端功能合入前，必须通过以下检查。主控验收时逐项对照，不通过禁止合入：

| # | 检查项 | 要求 |
|---|--------|------|
| 1 | 列表类数据 | 有分类、有排序、有空态（无数据时显示提示，不空白） |
| 2 | 导航类组件 | 点击有反馈、有对应关系、有高亮（当前选中项可见） |
| 3 | 关联展示 | A 和 B 有关联的，交互上必须体现关联（点击一侧，另一侧联动） |
| 4 | 状态差异 | 不同状态的数据必须有视觉区分（颜色/图标/标签） |
| 5 | 空态与边界 | 零数据、单条数据、超长文本、错误状态都要有合理呈现 |
| 6 | 响应反馈 | 点击、加载、保存、删除等操作必须有即时反馈（加载态/成功/失败） |

**核心理念**：功能完成 = 指令要求 + 交互闭环。指令描述了"做什么"，交互闭环是"做完"的底线。只完成指令要求、不完成交互闭环的，视为未完成，打回。

## 六、螺旋上升闭环

```
线路图 → 计划 → 看板 → 部署 → Loop巡查 → 发现问题
  ↑                                              │
  └──────── 老板判断"处理" ←───────────────────────┘
```

### 6.1 巡查机制

每轮开发完成后，Loop 自动巡查，发现问题自动回线路图草案池，等待下一轮老板定意图。

### 6.2 运维 Agent 职责（巡检 ≠ 监控）

运维 Agent 不是监控工具，监控只做表面检查（进程存活、心跳正常、磁盘空间）。运维 Agent 的职责是**架构合规性审计**：

| 级别 | 职责 | 检查内容 | 频率 |
|------|------|---------|------|
| **架构漂移** | 代码是否偏离 PRIME-DIRECTIVE | 数据模型是否与权威文档一致、三层关系是否完整、旧代码是否清理 | 每次合入前 |
| **治理漂移** | 状态不一致检测 | 里程碑进度 vs 方案进度 vs 看板状态是否一致、挂账是否无方案 | 每轮巡检 |
| **数据一致性** | 三层数据关系验证 | 里程碑→方案→看板 的级联回写是否正常、数据源是否单轨 | 每轮巡检 |
| **技术债** | 代码质量问题 | 覆盖率缺口、未关闭的审查意见、废弃代码残留 | 每轮巡检 |
| **基础设施** | 传统监控 | 服务存活、心跳、磁盘、日志异常 | 每轮巡检 |

**核心理念**：运维 Agent 的价值在于发现**架构漂移**（实现偏离了意图），而不是扫描代码 bug。代码 bug 是开发 Agent 和审查 Agent 的事。

### 6.3 巡查发现分类

- **架构漂移**：实现与权威文档不一致 → 回线路图草案池，标注「架构债」
- **治理漂移**：状态不一致、数据源双写 → 回线路图草案池，标注「治理债」
- **缺失项**：挂账无方案、功能缺口 → 回线路图草案池，标注「功能缺口」
- **技术债**：代码质量问题 → 回线路图草案池，标注「技术债」

## 七、与现有实现的差异

| 部分 | 现状 | 目标 |
|------|------|------|
| 线路图数据模型 | 从 epic 卡动态派生 | 独立 Project/Milestone/Step 模型 |
| 草案位置 | 计划页第一栏 | 搬到线路图页 |
| 里程碑 | 无独立概念 | 核心一等公民 |
| 三层关系 | 弱关联（卡名引用） | 级联依赖 + 状态回写 |
| 计划状态 | 五态（草案+执行四态） | 三态（已确认→部分执行→已完成） |
