# CCC 最高准则 — 三层全自动开发模式

> 版本：v1.0 · 定稿：2026-08-12 · 作者：老板 + qx1（外脑）
> 地位：**CCC 最高准则**，所有功能开发、流程设计、方案决策以此为唯一依据。

---

## 一、核心原则（一句话）

**线路图管未来，计划管当前，看板管正在进行时。老板定意图，机器管执行。**

---

## 二、三层架构

```
老板定意图
    │
    ▼
┌──────────────────────────────────────────────────────────────┐
│                     线路图（管未来）                           │
│                                                              │
│  项目总计划 → 里程碑 1 → 里程碑 2 → 里程碑 3                  │
│  草案池（待讨论的远期意图）                                    │
│                                                              │
│  数据模型：Project + Milestone + Step（独立持久化）            │
└──────────────────────────┬───────────────────────────────────┘
                           │
                ① 老板确认里程碑/方案
                           │
                           ▼
┌──────────────────────────────────────────────────────────────┐
│                      计划（管当前）                            │
│                                                              │
│  已确认 → 部分执行 → 已完成                                   │
│  （草案搬家到线路图后，计划只有三个执行态）                      │
│                                                              │
│  数据模型：Plan（方案 Markdown 文件）                          │
└──────────────────────────┬───────────────────────────────────┘
                           │
                ② 老板确认转卡
                           │
                           ▼
┌──────────────────────────────────────────────────────────────┐
│                   看板（管正在进行时）                          │
│                                                              │
│  待分派 → 执行中 → 机审 → 已回写 → 已关闭                     │
│  [Engine 全自动流转，无需人工干预]                              │
│                                                              │
│  数据模型：Card（任务卡 Markdown 文件）                        │
└──────────────────────────┬───────────────────────────────────┘
                           │
                ③ 老板合入批准
                           │
                           ▼
                      部署 + 上线
                           │
                    ┌──────▼──────┐
                    │ Loop 螺旋巡查 │
                    │ 发现问题     │
                    │ 回到线路图   │
                    └──────┬──────┘
                           │
                ④ 老板判断是否处理
                           │
                           ▼
                      回到线路图（下一轮）
```

## 三、三层数据关系

```
线路图.里程碑
  ├── 1:N → 计划.方案
  │         ├── 1:N → 看板.任务卡
  │         └── 状态回写 → 计划.方案.进度
  └── 状态回写 → 线路图.里程碑.进度
```

单向依赖 + 状态回写：
- 里程碑进度 = 子方案完成率
- 方案进度 = 子卡关闭率
- 卡状态 = Engine 全自动流转

## 四、人审节点（3 个，不可增减）

| 节点 | 位置 | 动作 | 为什么不能自动 |
|------|------|------|---------------|
| ① | 线路图 → 计划 | 老板确认里程碑/方案 | 意图判断——只有老板知道"现在做什么" |
| ② | 计划 → 看板 | 老板确认转卡 | 最后防线——确认拆卡方向正确 |
| ③ | 看板 → 部署 | 合入批准 | 代码 diff 终审——不可绕过 |

**只有这 3 个。** 其他一切流转由 Engine 自动完成。

## 五、自动化范围

| 环节 | 自动化 | 说明 |
|------|--------|------|
| 里程碑进度计算 | ✅ 全自动 | 子方案完成率实时回写 |
| 方案进度计算 | ✅ 全自动 | 子卡关闭率实时回写 |
| 卡状态流转 | ✅ 全自动 | Engine 派发→执行→机审 |
| 部署检查 | ✅ 全自动 | approve-merge 触发 |
| Loop 螺旋巡查 | ✅ 全自动 | Scheduler 定时巡检 |
| 巡查发现回线路图 | ✅ 全自动 | 自动生成草案/待办 |
| 意图定稿 | ❌ 人工 | 老板独有权力 |
| 里程碑确认 | ❌ 人工 | 节点 ① |
| 转卡确认 | ❌ 人工 | 节点 ② |
| 合入批准 | ❌ 人工 | 节点 ③ |

## 六、螺旋上升闭环

```
线路图 → 计划 → 看板 → 部署 → Loop巡查 → 发现问题
  ↑                                              │
  └──────── 老板判断"处理" ←───────────────────────┘
```

### 6.1 巡查机制

每轮开发完成后，Loop 自动巡查，发现问题自动回线路图草案池，等待下一轮老板定意图。

### 6.2 运维 Agent 职责（巡检 ≠ 监控）

运维 Agent 不是监控工具，监控只做表面检查（进程存活、心跳正常、磁盘空间）。运维 Agent 的职责是**架构合规性审计**：

| 级别 | 职责 | 检查内容 | 频率 |
|------|------|---------|------|
| **架构漂移** | 代码是否偏离 PRIME-DIRECTIVE | 数据模型是否与权威文档一致、三层关系是否完整、旧代码是否清理 | 每次合入前 |
| **治理漂移** | 状态不一致检测 | 里程碑进度 vs 方案进度 vs 看板状态是否一致、挂账是否无方案 | 每轮巡检 |
| **数据一致性** | 三层数据关系验证 | 里程碑→方案→看板 的级联回写是否正常、数据源是否单轨 | 每轮巡检 |
| **技术债** | 代码质量问题 | 覆盖率缺口、未关闭的审查意见、废弃代码残留 | 每轮巡检 |
| **基础设施** | 传统监控 | 服务存活、心跳、磁盘、日志异常 | 每轮巡检 |

**核心理念**：运维 Agent 的价值在于发现**架构漂移**（实现偏离了意图），而不是扫描代码 bug。代码 bug 是开发 Agent 和审查 Agent 的事。

### 6.3 巡查发现分类

- **架构漂移**：实现与权威文档不一致 → 回线路图草案池，标注「架构债」
- **治理漂移**：状态不一致、数据源双写 → 回线路图草案池，标注「治理债」
- **缺失项**：挂账无方案、功能缺口 → 回线路图草案池，标注「功能缺口」
- **技术债**：代码质量问题 → 回线路图草案池，标注「技术债」

## 七、与现有实现的差异

| 部分 | 现状 | 目标 |
|------|------|------|
| 线路图数据模型 | 从 epic 卡动态派生 | 独立 Project/Milestone/Step 模型 |
| 草案位置 | 计划页第一栏 | 搬到线路图页 |
| 里程碑 | 无独立概念 | 核心一等公民 |
| 三层关系 | 弱关联（卡名引用） | 级联依赖 + 状态回写 |
| 计划状态 | 五态（草案+执行四态） | 三态（已确认→部分执行→已完成） |
