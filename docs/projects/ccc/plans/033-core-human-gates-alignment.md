## 目标

把 CCC 的**三大核心人审节点（出卡 / 合入 / 验收）**的流程定义、状态语义、文档表述、后端逻辑与前端展示**彻底对齐**，消除歧义与冲突，形成一份可作为 CCC 流程根基的**权威基线**。所有流程与开发围绕这三节点展开，对齐后才能保证「文档说的、后端做的、前端显示的」三者一致。

## 背景

三大节点是 CCC 流程的根基，但经代码级核查，现状存在 **5 类问题**（证据见下）：

1. **三个节点定义不统一**：
   - 老板认知：**出卡 / 合入 / 验收**
   - 前端「人审闸门」（`legacy-chat/js/pages/opsPage.js:47-63`）渲染的却是：**确认方案 → 转卡 → 合入批准**（三个闸门，无验收）
   - 后端文档人审节点（`onboarding.md §3.5`）：① 方案确认 ② 转卡 ③ 合入 ④ 方案已完成验收——**实际是四个**
   - → 「出卡」在代码里被拆成「确认方案 + 转卡」两个闸门；「验收」完全没进人审闸门，只在 plansPage 显示验收进度条。
2. **合入批准措辞冲突（三处三个说法）**：
   - `onboarding.md §6.1/§6.3`：「合入批准（approve-merge.sh **机械门禁**）」
   - `server/board/roles.py:14`：「**老板合入批准 = 人审最终 diff**，任何人/工具都不能绕过」
   - `scripts/approve-merge.sh` 头部：「合入批准（**人审 diff 后**唯一常规动作）」
   - → 基线取 **roles.py:14 + approve-merge.sh（人审）**，机械校验只是脚本内一环。
3. **验收归属模糊**：
   - `onboarding.md §6.5`：方案「已完成」由**老板/验收席人工拍板**
   - `onboarding.md §7.3`：由**负责人/交付执行体**更新方案状态
   - → 谁执行「验收」动作没说清。
4. **前端标签显示不均**（老板观察「有些地方有显示有些没有」的实锤）：
   - `待办`（opsPage）vs `待分派`（boardPage）——同义不同标签
   - `合入`：opsPage 15 处 / consolePage 3 处 / plansPage 3 处 / **boardPage 仅 1 处**
   - `已确认`：仅 opsPage 有；`验收`：仅 plansPage 有（进度条，非闸门）
5. **「已确认」语义歧义**：
   - 方案五态「已确认」（老板确认方案）vs 基线里子任务「已确定」（Plan 模式深度调研后）——**状态机里没有区分**，也没有「已确定」中间态。

**关键基线（用户视角功能流，老板 2026-08-16 定）**：

```
草案（任意 IDE 可写 · 带工具标记）
  → 老板+主 Agent 探讨 → 确认方案入里程碑
  → 里程碑子任务（仅功能性规划 · 未深度调研）
  → 【Plan 模式调研：老板与任意 IDE 工具聊天 · 调查哪些已开发/需优化/没必要
     · 制定详细开发方案 · 留痕 · 不绑定具体工具】
  → 方案「已确定」
  → 老板确认 → 方案「已确认」（= 排队开发卡）
  → 转卡 → 开发卡「待办」（待分派）→ engine 自动消费
```

## 方案内容

### 一、定义权威基线（三节点统一语义）

**① 出卡** = 从「里程碑子任务（功能性规划）」到「开发卡（待办）」的完整通道，包含两个子闸门：
- 子闸门 A「方案已确定」：Plan 模式调研完成（详细开发方案 + 留痕），子任务从功能性规划升级为已调研。
- 子闸门 B「方案已确认」：老板确认 → 排队开发卡 → 转卡 → 开发卡「待办/待分派」。

**② 合入** = 已回写 → 机审（LLM 门禁）→ 机械校验（approve-merge.sh check_maintenance）→ **老板合入批准（人审 diff，不可绕过）** → 卡「已关闭」+ 触发部署检查。

**③ 验收** = 方案关联卡全部已关闭 → 交付执行体产出五大交付物（交付报告/CHANGELOG/RELEASE/Git Tag/可复跑验证）→ **老板/验收席按验收标准人工拍板「已完成」** → validate-plans.sh 机械校验兜底。

### 二、后端改动（状态机与语义）

1. **方案状态机补「已确定」中间态**：五态扩展为 草案 → **已确定** → 已确认 → 部分执行 → 已完成 → 作废。
   - 「已确定」= Plan 模式调研完成态（详细开发方案已定、留痕已存）。
   - 「已确认」= 老板确认的排队开发卡（与「已确定」明确区分）。
   - 落点：`server/board/plans.py` 状态校验 + `server/board/models.py`（如涉及）+ 前端 plans 页状态标签。
2. **「已确认」卡片语义标注**：计划页已确认卡 = 排队开发卡（明确其最终流向 = 转卡进开发看板待办）。

### 三、文档改动（消除冲突）

1. **合入批准措辞全文统一为「人审」**：修订 `onboarding.md §6.1/§6.3`（删除/纠正「机械门禁」误读，明确 approve-merge.sh = 人审后执行的脚本，内含机械校验一环）。
2. **验收归属明确**：修订 `onboarding.md §6.5/§7.3`——验收拍板归老板/验收席；交付执行体只产出交付物、不自行拍板「已完成」。
3. **§3.5 与 §6/§7 对齐**：人审节点①②（2026-08-16 决策）与 Doc-Gate/Delivery Gate 表述统一为三节点框架。
4. **权威源登记**：在 onboarding 或本方案备注登记三节点各自的权威文件（roles.py / approve-merge.sh / 本方案）。

### 四、前端改动（前后端对齐）

1. **人审闸门对齐三节点**：`opsPage.js` 人审闸门从「确认方案 → 转卡 → 合入批准」调整为老板认知的三节点（可含子闸门）：
   - 出卡（= 待确认方案 + 待转卡方案 两子块）
   - 合入（= 待合入批准）
   - **验收（新增闸门**：待验收/已交付待拍板的方案清单）
2. **标签统一**：全站统一 `待办`/`待分派`、`已确认`/`已确定` 语义与展示；boardPage 补「合入」相关状态展示（当前仅 1 处）。
3. **验收闸门数据源**：需后端提供「方案关联卡全关闭 + 交付物齐备 + 待老板拍板」的候选接口（或复用 plans 数据聚合）。

### 五、执行模型（红线约束）

- **平台自研红线**（ccc taskable:false，`onboarding.md §8.5`）：本方案**禁止出卡、禁止走 engine 自动派发**。
- 由**独立开发窗口人工评估 + 开发**（非 M1 主窗口，避免并行冲突），开发完成后交 **W1 验收席机审验收**。

### 升级（033 在 032 之上的延伸）

1. **032 P4「合入人审成文」→ 033 升级为三节点全链路基线**
   - 032 只把「合入人审」定义成文（`server/config/merge-executor-instruction.md`，人审 = 呈现真实 diff + 等老板批准）。
   - 033 把三大核心人审节点（出卡 / 合入 / 验收）的完整流程定义 + 权威基线系统化。**合入人审定义与 032 落地文档一致**，033 是范围扩展，非推翻。
2. **032 子项目层流程 → 033 补「已确定」中间态**
   - 032 骨架 = 里程碑 → 子项目 → 计划（逐步投入）→ 开发卡（三要素），**没有**「子任务（功能性规划）→ Plan 模式调研 → 已确定」环节。
   - 033 补全这一环（F1 状态机加「已确定」）。开发时须兼容 032 已实现的 convert_plan / validate-plans.sh（存量方案无「已确定」字段仅 WARN，不阻断）。
3. **032 P3 线路图页 → 033 ops 页人审闸门（新增前端面）**
   - 032 做了线路图页（右里程碑 / 左子项目 + 激活按钮）；033 新增/对齐 ops 页人审闸门（出卡 / 合入 / **验收**三节点）。前端不同页面，无冲突。
4. **032 P1 功能卡三要素 → 033 出卡基线依赖它**
   - 033 的「出卡」基线（确认方案 → 转卡 → 待办 → engine）**完全建立在 032 的 convert_plan / slices / 依赖硬约束之上**，是沿用非改造。

### 冲突（033 与 032 不一致处 + 处理指引）

1. **合入措辞（033 修订 onboarding §6.1/§6.3）**
   - 032 的 P4 落地文档已是「人审」措辞，但 **onboarding §6.1/§6.3 仍写「合入批准（approve-merge.sh 机械门禁）」**——032 P7 文档更新漏了这两处。
   - 033 要求统一为「人审」。**这是 032 遗留的文档不一致，033 修正它**，与 032 的合入定义一致，非根本矛盾。
2. **状态模型（033 插入「已确定」中间态）**
   - 032 五态（草案 → 已确认 → 部分执行 → 已完成 → 作废）没有「已确定」。033 在「草案」与「已确认」之间插入。
   - **开发时必须验证**：convert_plan 对「已确定」方案的处理、validate-plans.sh 不因新态误判、存量方案兼容（WARN 不 FAIL）。
3. **执行方式（032「M1 主窗口开发」vs 033「独立开发窗口」）**
   - 032 由 M1 主窗口直接开发；033 明确交独立开发窗口（避免并行冲突）。非流程冲突，是执行安排差异。
   - **开发窗口注意**：032 已落地的文件（`server/board/plans.py` / `roadmap.py` / `server/web/server.py`）改动须与 M1 主窗口的并行工作隔离，改前先 pull 对齐、改后显式提交。

### 结论

033 与 032 **方向一致、无根本矛盾**。033 是 032 的「三节点语义 + 前后端一致性」收口升级；冲突仅 onboarding §6.1/§6.3 措辞 + 新中间态兼容性两处，开发时按上述指引处理即可。
