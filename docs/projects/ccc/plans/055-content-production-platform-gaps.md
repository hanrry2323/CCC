## 一、底座定位（先钉死，避免方案越界）

CCC 引擎是「**代码任务的卡驱动执行 + 审核 + 合入 + 部署机器**」。

可复用能力（可靠性隔离，是底座最强项）：INFRA 类失败指数退避封顶 1800s 且不计预算（`failure_class.py:272-303`）；BUSINESS/PROTOCOL 双预算 + 达限终态打回挂人工（`failure_class.py:98-155`）；merge 冲突两次熔断（`phase2.py:1122-1130`）；push 失败保已回写态进冷却（`phase2.py:1131-1136`）；短命会话全局熔断 + 24h 强拆阈值熔断（`main.py:3472` / `1846`）；worktree 失败计数 + env-manifest 缺失 FAIL_FAST（`worktree.py:126-137`）；phase2 工作区脏整轮跳过（`phase2.py:1220-1228`）；deploy 失败卡保留已回写可重试（`phase2.py:1155-1165`）；scheduler 单任务超时/异常隔离（`scheduler.py:94-127`）；配额预检拒单（`main.py:3598-3607`）；管道静默故障落盘 `engine-pipeline.json` 上运维页（`pipeline_status.py`）。

**降级语义：冷却 / 跳过 / 重试 / 待人工，绝不伪造成功。** 这一条对内容产线是刚需——`xy-plan-011` 的阶段 0「让失败显形」正是要在业务侧对齐这个语义。

唯一与降级相反的硬约束：`consume_once` 遇工作区脏**整轮跳过**（`phase2.py:1226-1228`），属全有全无而非部分隔离。批量内容任务若共用同一工作区，会互相阻塞——**这是内容产线接底座时必须知道的一条**，建议内容任务走独立业务仓 worktree（`worktree.py` 已按项目隔离，天然满足）。

## 二、缺口清单

### 缺口 1 · 周期触发生产 —— 无（半有）

**现状**：有「一次性到点触发」，无「周期自生成」。

证据：`observer.py:1690 trigger_scheduled_ops` 扫卡头 `派发：scheduler` 且 `状态=待分派` 的卡；卡头有 `定时：HH:MM` 则 `now < schedule` 时跳过（`observer.py:1745-1749`），到点写 sidecar `reason=scheduler_triggered:<ts>`（`observer.py:1752-1756`），注释明写「Engine 不本地拉起」，远端 Worker 看到标记才认领；已触发过直接进 pending 不重复（`observer.py:1740-1742`）。

即：**卡必须先存在，触发一次性，到期不重生卡**。全仓 `server/engine/*.py` 无 cron 表达式解析；整机唯一 crontab 条目是 `5 6 * * * .dsh/ccc-prod-health.sh`（健康巡检，与生产无关）；`com.ccc.engine.plist` 是 `KeepAlive=true` 常驻轮询。

**架构纪律（不可破）**：`scheduler.py` 框架定义了 `TASK_TYPE_CHANGE`（`:46`），但 `_default_registry` 里**零变更类任务**；README:31 明写「只读巡检 + 变更类走卡（不绕过 Engine）」。`main.py:4042-4061 _embedded_scheduler` 起 daemon 线程按 `SCHEDULER_INTERVAL`（下限 30s，默认 60s）跑 5 个任务，**全部 `TASK_TYPE_READONLY`**：cluster-collect / loop-observer / observation-metrics / scheduled-ops-trigger / merge-dsh-trigger / log-janitor。

**缺口大小**：缺「每天自动生成一批新选题卡」的调度器。需要：cron 表达式解析 + 到点造卡（而非只打标）+ 造卡后走 `card_gate` 校验入池。

**风险**：造卡器是**变更类**能力，与「定时框架只读」的纪律正冲突。要么为内容选题单开一个受控的造卡通道（推荐，隔离风险），要么放开 `TASK_TYPE_CHANGE` 的默认注册（不推荐，会让所有变更都混进只读巡检框架）。

### 缺口 2 · 产出物入库 / 发布 —— 无（**划归业务仓侧，不在底座修**）

证据：`phase2.py:954 deploy_and_probe` 只干一件事——拉起 CCC 自己的 `server.web.server`（host/port 自 cfg）并轮询 `/health` 到 `_DEFAULT_HEALTH_TIMEOUT`（`phase2.py:962-971`）。全 `server/` 与 `scripts/` 无 publish / 媒体上传实现（唯一命中是 `scripts/deploy-ccc.sh:69` 的「安全性门禁拒绝发布」，指拒绝部署，非内容发布）。产物处理仅「代码产物存在性检查」：`main.py:2287`「exit 0 但无有效产物」打回、`main.py:626-683` 业务仓分支产物判定。

**缺口**：内容库登记 + 指纹 + 可复现证据包 + 展示台消费端。

**处置**：`xy-plan-011` 阶段 3 在业务仓侧实现，不动底座。理由：内容库是业务域模型，塞进 `server/engine/` 会让底座背上与代码任务无关的状态。

### 缺口 3 · 内容质量评估 —— 无（**划归业务仓侧，底座只借相位审席位**）

证据：底座有 `scripts/quality-score.py`（L1 机械质量分：圈复杂度 delta / mypy 错误 delta / 测试断言密度，增量不可劣化门禁）；`main.py:2350-2361` 测试/编译失败 = 硬打回；phase2 CC 审核独立会话出 verdict；合入门禁 `run_card_gates`。**内容质量：CCC 仓零实现。**

唯一相关内容在业务仓侧：`docs/projects/xy/README.md:35` 记录 xy 生产线「选题→文章→配图→脚本→配音→渲染→质量检查→本地归档」，是业务仓能力，不属底座。

**缺口**：内容分计算与闸 B。**但相位审能力现成**——phase2 机审（CC CLI 独立会话零共享上下文、`_read_audit_verdict` 解析 verdict、REJECT 计预算、达限挂人工）可直接复用为内容质量闸的判分席位，**底座这一层不需要开发**。

## 三、结论

| 缺口 | 在底座开发？ | 阻塞 xy-plan-011 哪一阶段 | 现有可借用 |
|---|---|---|---|
| 1 周期触发 | **是**（新开发） | 阶段 3 自动化调度 | 一次性到点触发框架 + 全套失败隔离 |
| 2 入库发布 | 否（业务仓侧） | 阶段 3 | 无 |
| 3 内容质量评估 | 否（业务仓侧） | 阶段 1 内容分 | **phase2 相位审席位可直接复用** |

**关键判断**：`xy-plan-011` 的阶段 0-2（让失败显形 / 内容质量可度量 / 接通 LLM 文案）**完全不依赖本方案任何一项缺口**——阶段 0-2 只在业务仓侧改。只有阶段 3 自动化调度需要缺口 1。

**这意味着 xy-plan-011 可以现在就开工，本方案不阻塞它。** 本方案应排在阶段 0-2 验证通过后、阶段 3 之前。

## 四、拍板点（1 个）

**造卡器放在哪一层。**

- **推荐**：内容选题造卡器**不进** `_default_registry`，单开受控通道——独立模块 + 独立卡前缀 + 造卡后必过 `card_gate` 校验，`card_gate.py:117-125` 的禁前缀断根机制可复用做白名单。代价：多一层模块，造卡逻辑与引擎调度解耦，故障域独立。
- **不推荐**：放开 `TASK_TYPE_CHANGE` 进 `_default_registry`。理由：会让变更类动作混进「只读巡检」框架，README:31 的纪律被打破，且任何变更类任务都能借这个口子绕过卡的门禁校验——正撞上 `card_gate` 断根要防的事。
- 若暂不做阶段 3，**本方案整个可推迟**，不影响 xy-plan-011 阶段 0-2。

## 五、不做什么（边界）

1. **不放开定时框架的只读纪律**——变更类动作必须先落卡（README:31）。
2. **不在底座做内容库、内容发布、内容质量分**——全归业务仓侧，见 §二。
3. **不动 `scheduler.py` 默认任务集**，除非拍板点选了「不推荐」那条。
4. **不碰 `server/config/config.env` 任何值**；不碰 `com.ccc.engine` / `com.ccc.web-server` / `com.ccc.tunnel-watchdog` 三个 launchd 项。
5. **不在本方案内实现**——本方案为缺口登记单，无实施内容。
