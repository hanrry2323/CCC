# 方案 · 核心流程定稿：里程碑 × 方案 × 功能卡（Step）四级模型

> 项目：ccc · 编号：ccc-plan-027 · 状态：草案 · 作者：Claude Code · 工具：ccc
> 批准：待老板确认方案
> 创建：2026-08-14 · 更新：2026-08-14
> 关联卡：无
> 关联方案：024（计划页重构 UI 按本模型实现）、022/023（UI 方案以本模型为准）

## 目标

把 CCC 核心开发流程定稿为「里程碑 → 方案 → 功能卡(Step) → 任务卡」四级模型：里程碑是核心容器，方案是设计单元，**功能卡即开发指令（一个功能一张卡）**，明确人审三节点、拆卡原则、两级卡内容与转卡粒度（A：一次全转）。本方案是流程层的**最高定义**，对齐并细化 PRIME-DIRECTIVE 三层架构；后续计划页 / 看板 / Engine 一切改造以此为流程依据。

## 背景

PRIME-DIRECTIVE 已定义三层（线路图 / 计划 / 看板），但内层结构未定稿，代码层存在多处断层（2026-08-14 老板与中枢多轮探讨收敛）：

1. **Step 悬空**：`roadmap.py` 的 `Milestone.steps` 字段真实数据零使用（现有 roadmap.md 全是 `- 状态/关联方案/描述`，无一条 `- [状态] 步骤`），且不关联方案、不关联卡、不参与进度。
2. **方案 ↔ 里程碑单向关联**：方案头部无「里程碑」字段（`create_plan` 不写），里程碑 `- 关联方案：` 单向写死；方案创建后不手动挂里程碑即「游离」，里程碑视角看不到、进度聚合断。
3. **拆卡格式两种并存 + 限 8 行**：表格格式（带依赖/执行体）与 ccc-plan `slices` 并存，`convert_plan` 限 8 行。
4. **方案「已完成」无自动推进**：`scheduler` 无「关联卡全关 → 方案已完成」逻辑；`observer` 只做反向告警（方案已完成但卡未关）。
5. **状态机三处规范冲突**：PRIME-DIRECTIVE 说方案三态（已确认/部分执行/已完成）、DOC-PROTOCOL §2.8 说五态（草案/已确认/部分执行/已完成/作废）、代码 `VALID_STATES` 是五态+已覆盖。
6. **计划层中间逻辑缺失**：方案「已确认待排期」与看板「待分派」关系不清——前者是**方案**等老板拍板（人审节点②），后者是**卡**等 Engine 派发；转化桥是节点② 的一次性转卡。

## 方案内容

### 一、四级流程模型

```text
线路图（草案池 + 里程碑）
  └── 里程碑（核心容器 · 关联方案）
        └── 方案（设计单元 · 头部含「里程碑：M1」双向关联）
              └── 功能卡清单（= Step · 节点② 审查对象）
                    └── 功能卡 = 任务卡（1:1 · 看板执行实体 · 两级内容）
```

- **里程碑 = 核心**：任何想法先定里程碑（技术栈 → 拆 10/20 个里程碑）。
- **方案 = 设计**：里程碑内要实现的事（前端设计 / 登录接口 / …），头部 `里程碑：M1` 双向关联。
- **功能卡 = 开发指令**：一个功能 = 一张功能卡 = 一张看板任务卡。**Step 与卡合体，无独立中间层**——这避免了三层拆解引入的进度中间层与状态漂移。

### 二、人审三节点（不可增减）

| 节点 | 位置 | 老板审什么 |
|------|------|-----------|
| ① | 线路图→计划 | 确认里程碑 / 方案 |
| ② | 计划→看板 | **确认方案拆出的功能卡清单**（拆卡方向）；确认即转卡 |
| ③ | 看板→部署 | 合入代码 diff |

- 「已确认待排期」= 方案等老板拍板功能卡方向（人审节点②）；
- 「待分派」= 功能卡已转成看板卡，等 Engine 派发。**两者分属方案层与卡层，通过节点② 的转卡动作转化。**

### 三、两级卡内容（功能卡 = 开发指令）

| 级别 | 内容 | 给谁看 |
|------|------|--------|
| **一级（人话）** | 标题 + 2-3 句「这一步做什么」 | 老板（节点② 审查）、看板导航 |
| **二级（实现）** | 功能背景 + 详细描述 + 开发要求 + 验收标准 | 执行体（Engine 派发后干活） |

- 卡文件结构：`## 目标（人话 2-3 句）` + `## 实现（详细，可选）`——二级是卡内展开，**不引入独立子卡**（执行单元不裂变，Engine 机制不动）。

### 四、拆卡原则（功能边界判定）

一张功能卡须同时满足：
1. **可独立交付**：有明确产出、能单独验收；
2. **验收标准可写**：对应 PRIME-DIRECTIVE 功能完成定义（指令要求 + 交互闭环）；
3. **依赖最小**：卡间尽量并行；必须串行的卡头标 `depends_on`；
4. **大小适中**：一次 agent 会话可完成。

**试金石**：验收标准是否 >5 条 → 是则说明它其实是 2 张卡，再拆。

### 五、方案状态机（定稿）

```text
已确认（待排期）→ 部分执行 → 已完成（终态）
   └── 作废（归档，不渲染）
```

- 「草案」概念**搬到线路图草案池**，方案层不再有草案态；
- **自动推进**：关联卡全关 → 方案自动「已完成」→ 里程碑进度自动更新；
- 代码 `VALID_STATES` 与 DOC-PROTOCOL §2.8、PRIME-DIRECTIVE 对齐。

### 六、转卡（粒度 A：一次全转）

- 节点② 确认功能卡清单 → convert 一次生成全部功能卡对应的任务卡；
- 转卡后方案 → 「部分执行」+ 写入关联卡；
- 执行顺序由卡头依赖/序号控制，**不在转卡时分批**（避免「部分转卡」状态漂移）。

### 七、进度回写链

```text
卡关闭率 → 方案进度（= 功能卡完成率）→ 里程碑进度（= 方案完成率）
```

因功能卡与卡 1:1，方案进度仍算关联卡关闭率，现有 `sync_plan_progress` / `sync_milestone_progress` 复用，无需新增中间层。
