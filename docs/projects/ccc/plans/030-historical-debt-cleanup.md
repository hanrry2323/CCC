# 方案 · CCC 历史包袱渐进清理

## 目标

用「盘点 → 隔离/备份 → 观察期 → 定日期删除」的渐进节奏，清理 CCC 平台从 Hub 时代至今积累的历史包袱（已退役 codex 分支、历史 T 卡、残留 worktree、demo 产物等）。旧物只作历史参考，不作历史包袱。不搞一次性大扫除，分步骤、可检查、长期执行。

## 背景

- CCC 自重构以来积累大量历史任务卡（84 个 T* 卡，已禁发新 T 卡）、已关闭历史卡（268 张）、43 个 codex/ 远端分支。Codex 已从「大脑」定位退役，但其分支多数未清理。
- 归档机制已存在（`docs/archive` / `.ccc/archive`），但缺少「何时删、谁删、怎么确认可删」的明确规则。
- 原则：CCC 向前发展。旧物可作历史参考（归档保留），但不能成为历史包袱（占空间、干扰扫描、误导新流程）。清理要趁早，越拖积压越重。

## 方案内容

### 核心节奏（每个垃圾源都走这套）

```
盘点建档 → 隔离/备份 → 观察期（无调用） → 定日期删除 → 清单留痕
```

### 垃圾源分类与处置策略

| 类别 | 规模 | 处置 | 是否删除 |
|------|------|------|----------|
| 历史 T* 任务卡 | 84 | 迁 `docs/archive/` | **不删**（历史参考） |
| 已关闭历史卡 | 268 | 迁 `docs/archive/` | **不删**（流程产物留档） |
| codex/ 远端分支 | 43 | 已合入 main → 备份卡 diff 后定日期删；未合入有成果 → 导出 patch → 观察期删 | **删除**（Codex 已退役） |
| 残留 worktree（业务仓 .ccc-wt） | 少量 | 合入确认后清理 | **删除** |
| 业务仓 demo/临时产物 | 若干 | 识别后清理 | **删除** |
| 过时方案/旧决策 | 少量 | 迁 `docs/archive/` | 归档，不删 |

### 分阶段执行（长期 · 每阶段可独立交付）

**阶段 1 · 盘点建档（一次性）**
- 扫全部 codex/ 分支：标记「已合入 main / 未合入有成果 / 未合入空壳」。
- 列历史 T 卡、已关闭卡、残留 worktree 清单。
- 产出 `docs/notes/2026-08-15-ccc-cleanup-inventory.md`（清理清单唯一真值）。

**阶段 2 · 历史参考物归档**
- T 卡 + 已关闭历史卡 → `docs/archive/`（迁移不删，保留目录结构可追溯）。
- 过时方案/旧决策 → `docs/archive/`。

**阶段 3 · codex 分支备份隔离**
- 已合入 main 的分支：确认卡 diff 已在 main → 标记「可删」，定删除日期。
- 未合入且有独立成果的分支：`git format-patch` 导出到 `docs/archive/codex-branches/`，标记「已备份，待观察」。

**阶段 4 · 观察期机制（长期运行）**
- 备份/隔离后进入观察期（建议 14 天；无引用且无调用的可缩短至 7 天）。
- 无调用判定：无新提交、无分支/卡引用、看板/脚本无引用、业务仓无 worktree 占用。
- 到期项在清理清单标记「可删」，人工复核后删除。

**阶段 5 · 定期清理节奏（长期）**
- 每次合入收口：顺手删已关闭卡的 codex/ 分支（收口时若分支已保留则一并清）。
- 每周五：对照清理清单，复核观察期到期项，执行删除或延期。
- 每月：汇总清理统计（删了多少分支、归档了多少卡），更新清单。

### 定期检查机制

- **清理清单**（`docs/notes/2026-08-15-ccc-cleanup-inventory.md`）是唯一真值，字段：`类别 / 对象 / 状态(待归档/已备份/观察中/可删/已删/保留) / 备份日期 / 观察到期日 / 删除日期 / 备注`。
- 触发时机：每次合入收口 + 每周五 + 每次方案状态变更。
- 检查动作：到期项复核 → 删除/延期 → 清单更新 → 提交。

## 验收标准

- [ ] `docs/notes/2026-08-15-ccc-cleanup-inventory.md` 清理清单建立，43 个 codex 分支逐一标记处置。
- [ ] 历史 T 卡、已关闭历史卡完成归档迁移，`docs/archive/` 结构可追溯。
- [ ] codex 分支：已合入 main 的完成备份+定删除日期；未合入有成果的完成 patch 导出。
- [ ] 观察期机制运行中：清理清单有「观察到期日」字段且按节奏复核。
- [ ] 每次收口顺手清理生效：新关闭卡的 codex 分支不再滞留。

## 功能卡

> 一阶段一张卡，按老板确认后转卡；多为运维/文档动作，可按阶段人工执行（转卡粒度 A）。

### 盘点建档

目标：扫全部 codex 分支和历史卡，产出《CCC 历史包袱清理清单》文档作为唯一真值。

实现：git 扫描 + 状态标记；产出 `docs/notes/2026-08-15-ccc-cleanup-inventory.md`。

验收：清单含 43 个 codex 分支逐一标记 + T 卡/历史卡/worktree 清单。

### 历史参考物归档

目标：把 T 卡、已关闭历史卡、过时方案迁入 `docs/archive/`，保留可追溯结构，不删除。

验收：归档迁移完成，`docs/archive/` 结构清晰可查。

### codex 分支备份隔离

目标：已合入 main 的分支定删除日期；未合入有成果的导出 patch 备份后进观察期。

验收：43 个 codex 分支全部处置（已备份/可删/保留），备份在 `docs/archive/codex-branches/`。

### 观察期与定期清理机制

目标：落地「备份→观察期→无调用→定日期删除」机制，每次收口顺手清、每周五复核、每月汇总。

验收：清理清单持续维护，观察期到期项按节奏执行删除/延期，有月度统计。

## 备注

- **风险**：删除分支前必须确认成果已备份（patch 或已合入 main）；观察期无调用判定需人工复核，避免误删仍有引用的分支。
- **依赖**：归档机制（已有）、合入收口流程（已有，收口时顺手清理）。
- **排期**：阶段 1-3 为一次性动作（1-2 周内完成）；阶段 4-5 为长期机制（持续运行）。
- **边界**：本方案只清理 CCC 平台自身的历史包袱；业务仓代码按业务仓各自红线处理，不越界。
