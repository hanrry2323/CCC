## 目标

坐实 CCC「标准化改造」体系（里程碑→子项目→方案→功能卡→任务卡→Engine 开发→交付收尾）在 6 个 taskable 项目（HP/XY/MX/CLA/QB/CLW）的真实达标情况，找出系统性短板，给出补强方案，使已标准化项目（HP/XY/MX）补齐闭环、未完成项目（CLA/QB）走完改造、封板项目（CLW）干净归档。

## 背景

老板指令（2026-08-19）：①HP/XY/MX 三个已标准化项目查漏补缺、找短板、制定弥补方案并优化；②CLA/QB/CLW 三个未标准化项目对标方案做改造。

审计方法：6 个子 Agent 并行逐项目核实六维度 + 代码机制核实（`approve-merge.sh` / `plans.py` / `roadmap.py` 源码级）。全程只读，证据带文件路径或命令输出。

## 核心发现（立意）

**短板不在「某个项目没做标准化」，而在标准化体系的「尾巴」系统性断裂。** 连最成熟的 HP（3.5/5）都断在尾部。四系统性断点 + 一红线事故，跨全部项目：

1. 状态回写断裂——「待验收」堆积 + roadmap 子项目映射缺陷
2. 交付层普遍缺失——6 项目仅 mx(001/002)/clw 有 deliveries
3. 机审门禁系统性绕过——卡体写「机审通过」但 board `machine_audit_passed=false`
4. 合入批准机制被绕过——CLA 9 张假关闭卡（代码未入 main）
5. 〔红线事故〕CLA cla020-028 假关闭，代码在 codex 分支未合 main

## 三、四系统性断点（根因级 · 跨全部项目）

### 断点① 状态回写断裂（最普遍）

**现象**：卡全关闭，方案卡在「待验收」、roadmap 卡在「计划中/待启动」。
- HP：11 个方案「待验收」对应卡全关闭；6+ 子项目标「计划中」实际已完成
- XY：6 方案「待验收」(进度100%)、roadmap M2/M3「待启动」，50 卡全关
- CLA：10 方案「待验收」(进度0/1)、roadmap M3「待启动」，14 卡全关
- MX：plan-004「待验收 2/3」三卡全关；plan-005「待验收 0/1」卡已关+机审通过

**根因（代码级核实）**：
1. **「待验收→已完成」靠人审，没跟上**：`plans.py:967` 注释明确——活跃卡全关只自动置「待验收」，「已完成」须老板/验收席人工拍板。这步设计上靠人，实际堆积没人清。
2. **roadmap 子项目状态映射缺陷（真 bug）**：`roadmap.py:812-817` `_sync_subproject_statuses` 只认方案「已完成」→子项目「已完成」，把「待验收」也归到「计划中」。结果卡全关、方案已待验收，roadmap 永远显示「计划中」——视觉断裂。

**机制本身是通的**：`approve-merge.sh:329 sync_plan_cards` → `plans.py:874 sync_plan_progress`，卡合入后会自动重算进度行、推进「部分执行→待验收」。断在最后两步：人审拍板 + 子项目映射。

### 断点② 交付层普遍缺失

**现象**：6 项目仅 MX(001/002) 和 CLW(3份) 有 deliveries。
- HP/XY/QB/CLA 全无 deliveries 目录
- **MX plan-003（被指定「第一个真跑通全流程」）也无 delivery-003**——engine 闭环成立，交付收尾这最后一步没闭合
- Delivery Gate（ccc-plan-017 已定稿）有机制无落地

### 断点③ 机审门禁系统性绕过

**现象**：卡体写「机审：通过」，board `machine_audit_passed=false`，靠老板合入批准手动放行。
- XY：22 卡 flag=false（含 xy033-051 全 19 张重立项卡）
- HP：21 卡 flag=false
- CLA：12 卡 flag=false（仅 cla017/018 通过）
- CLW：机审通过率 36%（9/25）

**根因**：机审 flag 与卡体审计结论两套来源不一致，合入批准不强制校验 flag。门禁形同虚设。

### 断点④ 合入批准机制被绕过（红线）

**现象**：卡标「已关闭+老板合入批准」，但代码未入 main。
- **CLA cla020-028（9卡）**：`git merge-base --is-ancestor` 全 NOT_IN_MAIN；`git ls-tree -d main src/` 无 workflow/api/frontend——M4-M5 核心业务代码从未进 main
- CLW clw027：分支孤岛未合入 main

## 四、〔红线事故〕CLA 假关闭——单独立项（不混入本方案）

cla020-028（9张卡）标「已关闭+老板合入批准」，但：
- 代码全部 NOT_IN_MAIN，只躺在 `codex/cla0XX-*` 分支
- main 的 src 仅有 adapters/common/crawlers/etl/scheduler，**无 workflow/api/frontend**
- 12 张卡 `machine_audit_passed=false` 却关闭
- cla020 维护区四问全空占位（本该「缺失=机审打回+合入拒绝」，实际放行）

**性质**：合入批准机制被绕过 + 机审门禁失效 + 维护区钩子未生效，三重红线失守。main 缺核心业务代码却显示任务完成。

**处理**：单独立事故核查方案（建议 ccc-plan-041），不混入标准化方案。核查 9 卡代码去向（补合 main or 作废重做）+ 合入机制为何放行 + 机审为何未拦。本方案 CLA 部分仅管「骨架走完到交付闭环」，前提是先解决假关闭。

## 七、体系级修复（四断点 · 平台自研红线：M1 主窗口直接开发 + 异席机审，不走 engine）

> **红线**：以下改动触及 `server/board/`（plans.py/roadmap.py）和 `scripts/approve-merge.sh`，属平台自研，registry ccc `taskable:false` 断根。一律 M1 主窗口直接开发 + 直接测试 + 异席机审（Codex 审），不写任务卡走 engine。

### 修复① 状态回写闭环（断点①）
1. **roadmap 子项目映射修复**：`roadmap.py:812-817 _sync_subproject_statuses` 增「待验收」态——方案「待验收」→子项目「待验收」（非「计划中」）。三态扩为四态：未启动/计划中/待验收/已完成
2. **待验收清理机制**：`sync_plan_progress` 已自动置「待验收」；补一个 ops 页/巡检告警——堆积超 N 天的「待验收」方案提示老板拍板（不自动推进，033 对齐：验收拍板归老板）

### 修复② 交付层制度化（断点②）
1. **validate-plans.sh 扩展**：方案「已完成」但无对应 delivery 报告 → 阻断（仿现有「卡关未收尾」阻断）
2. **Delivery Gate 落地检查**：ccc-plan-017 机制已定稿，补机械校验让它从「有 SOP」变「有门禁」

### 修复③ 机审门禁硬化（断点③）
1. **合入前强制 flag**：`approve-merge.sh` 校验 `machine_audit_passed=true`，false 拒绝合入（除非老板显式 override 并留因）
2. **机审区与 flag 同源**：消除卡体「机审：通过」与 board flag 两套来源不一致

### 修复④ 合入批准机制加固（断点④）
1. **合入前校验代码真入 main**：`approve-merge.sh` 合入后校验 `git merge-base --is-ancestor <分支> main`，未入 main 报错（防假关闭）
2. **维护区钩子硬化**：`approve-merge.sh` 现有机械校验维护区非占位，核实为何 cla020 空占位放行，补严
